# STT Handbook — Project Instructions

## 1. Проєкт

Цей репозиторій `stt-handbook` використовується для розробки посібника з теорії тестування програмного забезпечення.

Проєкт є довгостроковим. Робота над посібником виконується протягом багатьох сесій Claude Code та різними учасниками команди.

Основне завдання Claude — допомагати створювати, структурувати, редагувати та перевіряти матеріали посібника, зберігаючи послідовність, технічну точність і узгодженість між усіма розділами.

---

## 2. Мова

Основна мова посібника — українська.

Правила:

* Писати українською мовою.
* Загальноприйняті англомовні технічні терміни можуть залишатися англійською.
* Назви стандартів, методологій, фреймворків, програмних продуктів, API, протоколів та інших офіційних сутностей не перекладати без необхідності.
* Не використовувати російську мову.
* Один і той самий технічний термін повинен перекладатися однаково в усьому посібнику.

---

# 3. Джерело знань

## 3.1. Dataset

Директорія `dataset/` є основною базою знань проєкту.

У ній знаходяться Markdown-файли з інформацією, яка використовується для підготовки посібника.

```text
dataset/
├── books_pdf
├── dou
├── pptx_doc
├── QA_Bible
├── qalight
├── youtube
└── ...
```

Файли в `dataset/` необхідно розглядати як першочергове джерело інформації для написання посібника.

### Обов'язкове правило

Перед написанням нового теоретичного матеріалу Claude повинен спочатку перевірити відповідні матеріали в `dataset/`.

Не можна робити висновок, що інформація відсутня, не перевіривши `dataset/`.

---

## 3.2. Порядок використання джерел

Під час підготовки матеріалу використовувати такий порядок:

1. Матеріали в `dataset/`.
2. Інші Markdown-файли цього репозиторію.
3. Явні рішення та вказівки користувача.
4. Інші надійні джерела, якщо користувач прямо дозволив або попросив використовувати зовнішні джерела.

Якщо інформація з різних джерел суперечить одна одній:

* не приховувати суперечність;
* не робити необґрунтований вибір;
* повідомити про суперечність;
* запропонувати варіанти;
* за необхідності попросити користувача прийняти остаточне рішення.

---

# 4. Принцип достовірності

Claude не повинен вигадувати:

* визначення;
* факти;
* статистику;
* назви стандартів;
* номери стандартів;
* характеристики технологій;
* результати досліджень;
* посилання;
* цитати;
* джерела.

Якщо інформація невідома або недостатньо підтверджена, потрібно явно зазначити це.

Не видавати припущення за встановлений факт.

---

# 5. Посібник

Метою є створення системного навчального посібника з теорії тестування програмного забезпечення.

Матеріал повинен бути:

* структурованим;
* послідовним;
* технічно точним;
* зрозумілим для читача;
* придатним для навчання;
* узгодженим між розділами.

Необхідно уникати ситуацій, коли одна й та сама концепція визначається по-різному в різних розділах.

---

# 6. Структура матеріалу

Перед створенням нового розділу Claude повинен:

1. Перевірити структуру існуючого посібника.
2. Перевірити, чи вже існує матеріал на цю тему.
3. Перевірити відповідні файли в `dataset/`.
4. Визначити зв'язок нового матеріалу з уже існуючими розділами.
5. Не дублювати інформацію без необхідності.

Якщо новий матеріал логічно належить до існуючого розділу, не створювати новий розділ без потреби.

---

# 7. Термінологія

Термінологія повинна бути послідовною.

Перед використанням важливого терміна:

1. Перевірити його використання в `dataset/`.
2. Перевірити його використання в уже написаних розділах.
3. Якщо термін має декілька можливих перекладів — не змінювати його довільно.
4. Якщо існує суттєва термінологічна суперечність — повідомити користувача.

Особливо уважно ставитися до термінів:

* software testing;
* verification;
* validation;
* test case;
* test scenario;
* test suite;
* defect;
* bug;
* failure;
* error;
* test level;
* test type;
* test technique;
* test condition;
* test basis.

---

# 8. Визначення понять

При першому введенні важливого поняття:

1. Навести його назву.
2. Надати чітке визначення.
3. Пояснити його призначення.
4. За необхідності навести приклад.
5. Показати зв'язок з іншими поняттями.

Не використовувати поняття для пояснення іншого поняття, якщо перше ще не було визначене або пояснене.

---

# 9. Внутрішня узгодженість

Перед внесенням суттєвих змін перевіряти пов'язані документи.

Особливу увагу приділяти:

* визначенням;
* термінології;
* класифікаціям;
* нумерації;
* рівням тестування;
* типам тестування;
* тестовим технікам;
* життєвому циклу тестування;
* ролям;
* артефактам;
* процесам.

Якщо зміна одного документа може вплинути на інші документи, повідомити про це та перевірити пов'язані файли.

---

# 10. Робота з дублюванням

Перед створенням нового матеріалу перевірити, чи вже існує відповідна інформація.

Якщо інформація вже є:

* не дублювати її без потреби;
* посилатися на існуючий матеріал;
* або запропонувати реорганізацію.

Якщо дублювання необхідне для навчального пояснення, воно повинно мати іншу функцію і не суперечити оригінальному матеріалу.

---

# 11. Markdown

Усі матеріали посібника повинні бути у форматі Markdown.

Використовувати:

* `#` для заголовків;
* списки;
* таблиці;
* блоки коду;
* цитати;
* посилання;
* Mermaid або інші текстові діаграми, якщо вони справді покращують пояснення.

Не використовувати HTML без необхідності.

Не додавати зайве форматування.

---

# 12. Код та приклади

Приклади коду повинні бути:

* синтаксично зрозумілими;
* мінімальними;
* пов'язаними з матеріалом;
* достатніми для демонстрації концепції.

Не створювати складний код лише заради прикладу.

Якщо приклад є концептуальним і не призначений для виконання, це потрібно чітко зазначити.

---

# 13. Робота з джерелами

Якщо матеріал базується на конкретному джерелі, його походження повинно бути зрозумілим.

Не вигадувати бібліографічні дані.

Не створювати неіснуючі посилання.

Не вигадувати номери стандартів.

Якщо користувач просить провести дослідження або актуалізувати інформацію, необхідно використовувати актуальні зовнішні джерела та чітко відокремлювати їх від матеріалів `dataset/`.

---

# 14. Робота з попередніми рішеннями

Якщо під час попередніх сесій було прийнято важливе рішення, Claude повинен намагатися зберегти його послідовність.

До важливих рішень належать:

* структура посібника;
* термінологія;
* класифікації;
* порядок розділів;
* правила оформлення;
* методика пояснення;
* прийняті визначення;
* відхилені підходи;
* домовленості щодо джерел.

Не змінювати раніше прийняте рішення без явної причини.

---

# 15. Claude Memory

Claude може використовувати механізми довготривалої пам'яті, зокрема `claude-mem`, якщо вони встановлені в локальному середовищі користувача.

Пам'ять Claude не є заміною репозиторію.

Розділяти:

* `dataset/` — джерело фактичних знань;
* Markdown-файли посібника — результат роботи;
* `CLAUDE.md` — правила роботи;
* Git — спільна історія та джерело істини для команди;
* Claude Memory — контекст попередніх сесій.

Критично важливі рішення повинні бути зафіксовані у файлах репозиторію, а не лише в пам'яті Claude.

---

# 16. Командна робота

Репозиторій використовується кількома учасниками команди.

Не припускати, що знання, які існують лише в локальній пам'яті одного користувача, доступні іншим членам команди.

Усе, що має бути доступним команді, повинно бути збережено в Git-репозиторії.

Не додавати персональні файли пам'яті Claude до Git без явного рішення команди.

---

# 17. Git

Не виконувати автоматично:

* `git commit`;
* `git push`;
* `git reset`;
* `git rebase`;
* видалення файлів;
* масове перезаписування документів.

Такі операції виконувати лише після явної вказівки користувача.

Перед великими змінами показати, які файли будуть змінені.

---

# 18. Робочий процес

При отриманні нового завдання:

### Крок 1 — зрозуміти завдання

Визначити:

* що саме потрібно створити або змінити;
* у якому розділі;
* які документи пов'язані із завданням.

### Крок 2 — пошук

Перевірити:

```text
dataset/
```

та пов'язані Markdown-файли репозиторію.

### Крок 3 — аналіз

Визначити:

* існуючі визначення;
* термінологію;
* пов'язані концепції;
* можливі суперечності;
* дублювання.

### Крок 4 — підготовка

Створити або змінити необхідний матеріал.

### Крок 5 — перевірка

Перевірити:

* логіку;
* термінологію;
* структуру;
* Markdown;
* внутрішню узгодженість;
* відповідність джерелам.

### Крок 6 — результат

Повідомити:

* що змінено;
* які файли змінено;
* які питання залишилися;
* чи є потенційні суперечності.

---

# 19. Заборонено

Claude не повинен:

* вигадувати джерела;
* вигадувати цитати;
* вигадувати технічні факти;
* без попередження змінювати усталену термінологію;
* видаляти інформацію без причини;
* переписувати весь документ при необхідності локальної зміни;
* створювати дублікати існуючих матеріалів;
* автоматично виконувати Git-операції, які змінюють історію;
* вважати власну пам'ять важливішою за фактичні файли репозиторію.

---

# 20. Головний принцип

Працюй не як одноразовий генератор тексту, а як постійний помічник у розробці одного великого технічного посібника.

Перед написанням:

> Search → Read → Understand → Write → Check consistency.

Джерело знань:

> `dataset/`

Джерело поточного стану проєкту:

> Git repository.

Правила роботи:

> `CLAUDE.md`

**Словник термінів і скорочень:**

> `TERMINOLOGY.md` — визначення критичних термінів з прикладами та джерелами
> `ABBREVIATIONS.md` — перелік скорочень, що використовуються в посібнику

Контекст попередніх сесій:

> Claude Memory / `claude-mem`, якщо доступний.

Якщо є невизначеність або суперечність — не вигадуй відповідь. Покажи проблему та запропонуй варіанти рішення.
