# STT Handbook — Project Instructions

## 1. Проєкт

Цей репозиторій `stt-handbook` використовується для розробки посібника з теорії тестування програмного забезпечення.

Проєкт є довгостроковим. Робота над посібником виконується протягом багатьох сесій Claude Code та різними учасниками команди.

Основне завдання Claude — допомагати створювати, структурувати, редагувати та перевіряти матеріали посібника, зберігаючи послідовність, технічну точність і узгодженість між усіма розділами.

---

## 2. Мова

Основна мова посібника — українська.

Правила:

* Писати українською мовою.
* Загальноприйняті англомовні технічні терміни можуть залишатися англійською.
* Назви стандартів, методологій, фреймворків, програмних продуктів, API, протоколів та інших офіційних сутностей не перекладати без необхідності.
* **Не використовувати російську мову**.
* Один і той самий технічний термін повинен перекладатися однаково в усьому посібнику.

### 2.3. Правило перевірки

Перед комітом будь-якого файлу:

1. **Переглянути файл на предмет російських слів та конструкцій.**

2. **Виявлення та заміна російських букв:**

   **Перевірка на російські літери (яких немає в українській):**
   - "ё" (йо) — **ніколи** не використовується в українській (напр. "всё" → "все")
   - "ы" (ви) — **типова російська гласна**, замінити на "и" або переписати слово (напр. "ты" → "ти", "сын" → "син")
   - "щ" (ща) — **виключно російська буква**, заміна залежить від контексту (напр. "щука" → "щупак" або перепис)
   - "э" (е) — російська гласна в певних позиціях
   - "ю" та "я" — в деяких випадках мають російське походження (потребує аналізу)

   **Алгоритм дії при виявленні російської літери:**
   1. Знайти слово, що містить російську букву
   2. Перевірити, чи це **технічний термін** (чи скорочення), де допустима іноземна мова
   3. Якщо **не технічний термін** — знайти питомо **український еквівалент**:
      - Перевірити словник (TERMINOLOGY.md, Словник УАПП 2019)
      - Якщо словникового еквіваленту немає — переписати слово українською конструкцією
   4. Замінити на знайдену українську версію
   5. **Документувати** заміну в git commit message

   **Практичні приклади пошуку та заміни російських букв:**
   - "ы": "тестирование" → "тестування", "системы" → "системи", "методы" → "методи"
   - "ё": "всё" → "все", "ё-мое" → "о-мое" (якщо технічне) або переписати
   - "щ": "щоб" (нормально в укр.), але "щенок" → "цуценя"
   - "э": "тест" (укр. "е"), "эффект" → "ефект"

3. **Використати пошук за ключовими словами (базовий набір):**
   - Російські частини мови: "и" (замість "та/і"), "из" (замість "з")
   - Російські слова: "Исчерпывающее", "Белый", "тестирование", "Черный", "Серый"

4. **Перевірити граматичні та синтаксичні форми:**
   - ✓ Узгодження родів (один/одна/одне)
   - ✓ Вищий ступінь порівняння (без "найбільш/найменш")
   - ✓ Природність виразів (без дослівних перекладів із російської)
   - ✓ Множина іменика в правильному відмінку (межи → межі)
   - ✓ Наголос у прикметниках (Ранне → Раннє)

5. **Типові помилки з Глави 2 (QA/Testing Domain):**
   - ❌ "юзабіліті" → ✓ "зручність використання"
   - ❌ "програмського продукту" → ✓ "програмного продукту"
   - ❌ "акт прийманості" → ✓ "акт здачі-приймання"
   - ❌ "на однакові дні" → ✓ "з перших днів спринту / на рівних"
   - ❌ "у віку LLM" → ✓ "в еру генеративних LLM"
   - ❌ "чіткі межи ролі" → ✓ "чіткі межі ролей та відповідальності"

### 6.1. Структурування розділів за розміром

**Рекомендовані розміри файлів:**
- **Маленький розділ (Subsection)**: 100-200 рядків
- **Середній розділ (Chapter)**: 300-500 рядків
- **Великий розділ**: до 700 рядків
- **Дуже великий розділ (>700 рядків)**: розділити на 2-3 підрозділи

**Сигнали для розділення розділу:**
- 🔴 > 1000 рядків — обов'язково розділити
- 🟠 700-1000 рядків — розглянути розділення
- 🟡 500-700 рядків — можливо розділити для бонус читаності
- 🟢 < 500 рядків — залишити як є

**Структура папки (приклад):**
```
dist/
└── Частина 1/
    ├── Вступ та фундаментальні основи/
    │   ├── Глава 1/
    │   │   └── Вступ до тестування.md (708 рядків - це максимум)
    │   ├── Глава 2/
    │   │   └── Основи контролю якості.md
    │   ├── Глава 3/
    │   │   └── Процеси та цикли тестування.md
    │   └── Глава 4/
    │       └── Психологія та принципи тестування.md
```

**Правило розділення:**
- Якщо файл > 1000 рядків → розділити на підрозділи
- Якщо підрозділ > 500 рядків → розглянути додаткове розділення
- Підрозділи можна зберігати як один файл або розділити на 1.1, 1.2, ... файли
- Придержуватися однакової структури всередину однієї ЧАСТИНИ

### 8.1. Quiz питання та самоперевірка

Питання для самоперевірки повинні мати чітку структуру:

**Структура quiz питання:**
1. **Контекст/сценарій** — опис ситуації для аналізу
2. **4 варіанти відповіді** (A, B, C, D) — логічно завершені
3. **Правильна відповідь** — чітко визначена
4. **Пояснення** — чому це правильна відповідь

**Критерії якості:**
- ✓ Вимірюють розуміння, не просто запам'ятовування
- ✓ Базуються на концепціях розділу
- ✓ Мають логічно завершений сценарій
- ✓ Всі варіанти відповідей правдоподібні (не очевидна правильна)

**Типові помилки:**
- ❌ Змішування кількох концепцій в одному питанні
- ❌ Неправильна класифікація відповідей (розпливчастість)
- ❌ Надто складні або надто прості питання

### 8.2. Міти та парадокси в тестуванні

При створенні розділів про "міти" або "парадокси", дотримуватися структури:

**Структура кожного міту:**
1. **Міт** (заголовок) — коротко сформульована помилкова убеждение
2. **Помилкова убеждение** — що люди помилково думають
3. **Реальність** — що насправді є правдою
4. **Чому це важливо** — практичні наслідки для тестування
5. **Приклад** — реальна ситуація або сценарій

**Приклад добре структурованого міту:**
```markdown
### Міт: "Тестування затримує розробку"

**Помилкова убеждение:**
Коли тестувальники вимірюють час, тестування виглядає як додаткові витрати часу.

**Реальність:**
Раннє тестування (на етапі розробки) економить час на пізніші етапи.

**Чому це важливо:**
Дефект, знайдений на ранній стадії, коштує у 10-100 разів менше,
ніж дефект, знайдений у production.

**Приклад:**
- Дефект на етапі розробки: 1 година виправлення
- Дефект у production: 10+ годин (включаючи реакцію на скарги)
```

**Правила перевірки мітів:**
- ✓ Кожен міт має четку "реальність", не розпливчату
- ✓ Причини узгоджені з фактичною практикою
- ✓ Приклади реальні, не надумані
- ✓ Міти враховані у практичних завданнях

### 8.3. Розмежування концепцій

Коли розробляються розділи про Related concepts (наприклад, Testing vs Debugging), дотримуватися такої структури:

**Структура порівняння:**
1. **Визначення кожної концепції** (окремо і чітко)
2. **Таблиця порівняння** (схожість та відмінності)
3. **Практичні приклади** (де вони застосовуються)
4. **Часна шкала** (коли в lifecycle вони відбуваються)

**Приклад таблиці порівняння:**
```markdown
| Аспект | Тестування | Дебаггінг |
|--------|-----------|----------|
| **Мета** | Знайти дефекти | Знайти причину дефекту |
| **Хто** | Тестувальник | Розробник |
| **Інструменти** | Тест-кейси, метрики | Debugger, логи |
| **Результат** | Bug Report | Fixed code |
| **Методи** | Систематичні техніки | Аналіз, експериментування |
```

**Правила розмежування:**
- ✓ Не допускати змішування концепцій в одному абзаці
- ✓ Кожна концепція має свої інструменти та методи
- ✓ Чітко показати sequence (одна → друга)
- ✓ Навести приклади обох сценаріїв

Якщо інформація вже є:

* не дублювати її без потреби;
* посилатися на існуючий матеріал;
* або запропонувати реорганізацію.

Якщо дублювання необхідне для навчального пояснення, воно повинно мати іншу функцію і не суперечити оригінальному матеріалу.

Приклади коду повинні бути:

* мінімальними;
* пов'язаними з матеріалом;

Не створювати складний код лише заради прикладу.

Якщо приклад є концептуальним і не призначений для виконання, це потрібно чітко зазначити.

### 12.1. QR-коди та інтерактивні елементи

Для посилань на зовнішні ресурси можна використовувати QR-коди через qrserver API:

**Формат:**
```markdown
![QR: Опис ресурсу](http://api.qrserver.com/v1/create-qr-code/?size=200x200&data=URL&margin=10)
```

**Правила:**
- Розмір: 200x200px (читабельний, не громіздкий)
- Margin: 10 (простір навколо)
- Data: повна URL до ресурсу
- Опис повинен чітко описувати, куди веде посилання

**Коли використовувати:**
- Посилання на довгі URL-адреси
- Посилання на відео-ресурси
- Посилання на практичні проекти GitHub
- Посилання на сторонні матеріали

**НЕ використовувати для:**
- Внутрішніх посилань всередину посібника
- Посилань на файли в папці `dist/`

# 13. Робота з джерелами

Якщо матеріал базується на конкретному джерелі, його походження повинно бути зрозумілим.

Не вигадувати бібліографічні дані.

Не створювати неіснуючі посилання.

Не вигадувати номери стандартів.

Якщо користувач просить провести дослідження або актуалізувати інформацію, необхідно використовувати актуальні зовнішні джерела та чітко відокремлювати їх від матеріалів `dataset/`.

### 13.1. Посилання на dataset файли

Всі посилання на файли в `dataset/` повинні використовувати **GitHub URLs**, не локальні шляхи:

**✅ Правильно:**
```markdown
[Міфи про тестування](https://github.com/STT-VITI-22/stt-handbook/blob/main/dataset/articles/qalight/parsed/osnovi/mifi-pro-testuvannia.md)
```

**❌ Неправильно (локальні шляхи):**
```markdown
[Міфи про тестування](../../../../../../dataset/QALight/parsed/osnovi/mifi-pro-testuvannia.md)
[Міфи про тестування](/dataset/QALight/parsed/osnovi/mifi-pro-testuvannia.md)
```

**Причини:**
- Локальні шляхи ломаються при переміщенні файлів
- GitHub URLs працюють з будь-якого пристрою
- Читачам легше кліка́ти по посиланням в GitHub веб-інтерфейсі
- Ремонт легше відслідити через Git historyu

**Правило перевірки перед коммітом:**
```bash
# Знайти всі посилання на dataset:
grep -r "dataset/" dist/

# Замінити на GitHub URL, якщо знайдено локальні шляхи
```

### 13.2. Таблиці та довідкові матеріали

Таблиці з посиланнями повинні мати чіткою структуру:

**Правильно:**
```markdown
| Ресурс | Посилання | Тип |
|--------|-----------|-----|
| DOU QA Roadmap | [Дорожна карта](https://dou.ua/qa-roadmap) | Карта навичок |
| QALight Основи | [Посібник](https://github.com/.../dataset/articles/qalight/parsed/osnovi/) | Курс |
```

**Структура таблиці:**
- Стовпець 1: Назва ресурсу
- Стовпець 2: Посилання (формат Markdown)
- Стовпець 3: Тип/категорія ресурсу (опціонально)

**Правила для таблиць:**
- Всі посилання повинні бути актуальні
- Назва посилання повинна описувати вміст
- Перевірити, що посилання працює (не робити неживих посилань)
- Не кидати таблиці в кінець розділу без контексту

**Посилання на словники:**
- Для скорочень та термінів використовувати посилання на `ABBREVIATIONS.md` та `TERMINOLOGY.md`
- Приклад: "Див. [ABBREVIATIONS.md](./ABBREVIATIONS.md#rtm---requirements-traceability-matrix) для визначення RTM"
- Не дублювати визначення в таблицях, якщо вони вже задокументовані

# 15. Claude Memory та CHANGELOG.md

Claude може використовувати механізми довготривалої пам'яті, зокрема `claude-mem`, якщо вони встановлені в локальному середовищі користувача.

## Основа запам'ятовування: CHANGELOG.md

**CHANGELOG.md** є основним джерелом для запам'ятовування контексту попередніх сесій. На початку кожної нової сесії Claude повинен:

1. **Прочитати CHANGELOG.md** цілком
2. **Звернути увагу** на розділи:
   - `[Невипущено]` — поточні неопубліковані зміни
   - **Added / Додано** — нові функції та матеріали
   - **Fixed / Виправлено** — вирішені проблеми
   - **Changed / Змінено** — змінена функціональність
   - **Removed / Видалено** — видалена функціональність
   - **BREAKING CHANGES** — критичні зміни, що порушують сумісність

3. **Врахувати всі коментарі** в CHANGELOG:
   - (feature) — нові функції та додатки
   - (fix) — виправлення помилок
   - (docs) — зміни в документації
   - (refactor) — переробка коду без зміни функціональності
   - (Type) — покращення типів/узгодженості
   - (perf) — поліпшення продуктивності
   - (test) — додання тестів

4. **На кінці сесії** Claude повинен оновити CHANGELOG.md розділом `[Невипущено]` з усіма змінами:
   ```markdown
   ## [Невипущено] / Unreleased

   ### Added / Додано
   - (feature) опис нової функції
   - (docs) опис нового документа

   ### Fixed / Виправлено
   - (fix) опис виправлення

   ### Changed / Змінено
   - (refactor) опис переробки
   ```

## CHANGELOG як контекстна база

Замість розповідання на тему "я забув контекст", Claude повинен:

1. Завжди **читати CHANGELOG.md** на початку сесії
2. **Розуміти стан проекту** з останніх змін
3. **Не дублювати роботу**, перевіривши розділ `[Невипущено]`
4. **Слідкувати за BREAKING CHANGES**, які можуть вплинути на роботу
5. **Оновлювати CHANGELOG** за результатами роботи

## Розділяти ролі:

* `dataset/` — джерело фактичних знань;
* Markdown-файли посібника — результат роботи;
* `CLAUDE.md` — правила роботи;
* `TERMINOLOGY.md` — словник термінів;
* `ABBREVIATIONS.md` — перелік скорочень;
* **`CHANGELOG.md` — контекст та історія змін (основа запам'ятовування)**;
* Git — спільна історія та джерело істини для команди;
* Claude Memory (`claude-mem`) — додатковий контекст, якщо доступний.

## Формат CHANGELOG

CHANGELOG дотримується формату [Keep a Changelog](https://keepachangelog.com/uk/):

- **[Невипущено]** — зміни, які ще не випущені
- **[X.X.X] - YYYY-MM-DD** — версії з датами виходу
- **Added** — нові функції
- **Fixed** — виправлення помилок
- **Changed** — зміни функціональності
- **Removed** — видалена функціональність
- **Deprecated** — функції, що застарівають
- **BREAKING CHANGES** — зміни, що порушують сумісність

Критично важливі рішення повинні бути зафіксовані в CHANGELOG.md та файлах репозиторію, а не лише в пам'яті Claude.

### 15.1. Запис про завершену главу в CHANGELOG

При завершенні розділу, перед коммітом додати запис до `CHANGELOG.md`:

**Формат запису про завершену главу:**
```markdown
### Added / Додано
- (docs) Глава 1: Вступ до тестування (708 рядків, v1.0)
  - 5 підрозділів (1.1-1.5)

  - Посилання на 12 dataset файлів (GitHub URLs)

### Fixed / Виправлено
- (docs) Оновлено посилання на dataset з локальних шляхів на GitHub URLs
- (fix) Виправлено 15+ мовних помилок (суржик, російські лазерки, граматика)
```

**Що включити в запис:**
- ✓ Номер та назва глави
- ✓ Версія розділу (v1.0, v2.0, тощо)
- ✓ Кількість рядків (для розуміння обсягу)
- ✓ Кількість підрозділів
- ✓ Практичні завдання (якщо є)
- ✓ Quiz питання (якщо є)
- ✓ Інтерактивні елементи (QR-коди, таблиці)
- ✓ Основні дефекти/поправки (мовні, посилання, логіка)

**Приклад повної записи:**
```markdown
### Added / Додано
- (docs) Глава 3: Процеси та цикли тестування (450 рядків, v1.0)
  - 5 підрозділів (3.1-3.5)

  - Посилання на 8 dataset файлів

- (docs) Розширено розділ 3.4 (Матриці) з новими прикладами

### Fixed / Виправлено
- (fix) Виправлено помилку в терміні "Requirements Traceability" (RTM)
- (fix) Оновлено посилання на QALight файли
```

**Момент заповнення:**
- ✓ Після завершення розділу
- ✓ Перед створенням git commit
- ✓ Коли файл готовий до публікації
