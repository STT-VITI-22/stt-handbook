### Software Testing / Тестування ПЗ

**Англійська:** Software Testing
**Українська:** Тестування програмного забезпечення (ПЗ)

**Визначення:**
> Процес перевірки відповідності заявлених до продукту вимог та реально реалізованої функціональності, що відбувається шляхом спостереження за його роботою в штучно створених ситуаціях та на обмеженому наборі тестів, вибраних визначеним чином.

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`
- `dataset/articles/qalight/parsed/osnovi/shcho-take-testuvannia-programnogo-zabezpechennia.md`

**Приклад у реченні:**
"Тестування ПЗ є ключовою частиною забезпечення якості продукту."

### Verification (В-процес) / Верифікація

**Англійська:** Verification
**Українська:** Верифікація (або: перевірка під час розробки)

**Визначення:**
> Статична практика перевірки документів, дизайну, архітектури, коду та інших артефактів розробки. Відповідає на питання: "Чи ми будуємо продукт правильно?" (Are we **building** the product right?)

**Ключові характеристики:**
- Статична (код не виконується)
- Проводиться розробниками та аналітиками
- Перевірка артефактів: документація, дизайн, архітектура, код
- Проводиться під час розробки

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`

**Приклад у реченні:**
"Верифікація коду виконується через code review, статичний аналіз та перевірку документації."

### Validation (V-процес) / Валідація

**Англійська:** Validation
**Українська:** Валідація (або: динамічна перевірка)

**Визначення:**
> Динамічний процес оцінки кінцевого продукту через тестування. Необхідно перевірити, чи відповідає програмне забезпечення очікуванням і вимогам клієнта та користувачів. Відповідає на питання: "Чи ми будуємо потрібний продукт?" (Are we **building** the **right** product?)

**Ключові характеристики:**
- Динамічна (код виконується)
- Проводиться тестувальниками та QA-фахівцями
- Тестування на реальних даних та сценаріях
- Проводиться після розробки/на готовому продукті

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`

**Приклад у реченні:**
"Валідація продукту включає функціональне тестування, тестування юзабіліті та приймальне тестування."

**Различие:**
| Верифікація | Валідація |
|---|---|
| Чи ми будуємо **правильно**? | Чи ми будуємо **потрібне**? |
| Статична | Динамічна |
| Розробка | Тестування |
| Документи, код, дизайн | Реальний продукт, сценарії |

### Defect / Дефект

**Англійська:** Defect
**Українська:** Дефект

**Визначення:**
> Неправильність у програмному продукті, яка проявляється при виконанні коду під час тестування або в продакшені. Дефект — це об'єктивна властивість кода, яка існує незалежно від того, що хтось про неї знає.

**Синоніми (майже):**
- Bug (баг) — популярний термін, синонімічний дефекту
- Fault (збій) — деякі джерела розрізняють, але в практиці часто взаємозамінні

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md` — "Баг – дефект; невідповідність фактичного результату виконання програми очікуваному результату."

**Приклад у реченні:**
"Дефект у функції сортування призвів до неправильного впорядкування результатів."

### Error / Помилка

**Англійська:** Error
**Українська:** Помилка

**Визначення:**
> Дія або рішення розробника, яке приводить до створення дефекту. Помилка — це причина, дефект — це наслідок.

**Розрізнення:**
- **Error (Помилка)** — дія розробника, яка створює дефект (причина)
- **Defect (Дефект)** — результат цієї помилки в коді (наслідок)
- **Failure (Збій)** — видимий результат виконання коду з дефектом (прояв)

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md` — "Помилка – дія, після якої виникає неправильний результат."

**Приклад у реченні:**
"Помилка розробника (забув ініціалізувати змінну) привела до дефекту в коді, який виявився відправкою невизначеного значення користувачеві (збій)."

---

### Failure / Збій

**Англійська:** Failure
**Українська:** Збій (або: невідповідність функціональності)

**Визначення:**
> Невідповідність фактичного результату роботи системи чи компонента тому результату, який очікували. Збій — це видимий прояв дефекту при виконанні.

**Розрізнення від дефекту:**
- **Дефект** — проблема в коді (потенційна)
- **Збій** — прояв дефекту під час виконання (спостережувана невідповідність)

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md` — "Збій – невідповідність фактичного результату роботи системи чи компонента тому результату, який очікували."

**Приклад у реченні:**
"Дефект у функції забезпечив збій: користувач очікував число 10, але програма вивела 15."

---

## Деталь: Error → Defect → Failure (ланцюжок)

```
Помилка (Error)
  ↓
Дефект (Defect у коді)
  ↓
Збій (Failure при виконанні)
```

**Приклад:**
1. **Error:** Розробник написав `x = x + 1` замість `x = x - 1`
2. **Defect:** В коді існує неправильна операція
3. **Failure:** При виконанні програма видає неправильний результат

### Test Case / Тестовий випадок

**Англійська:** Test Case
**Українська:** Тестовий випадок (або: тест-кейс)

**Визначення:**
> Тестовий артефакт, що складається з набору умов (передумов), дій та очікуваних результатів. Тестовий випадок призначений для перевірки конкретної функціональності або поведінки системи.

**Компоненти тестового випадку:**
- **Передумови (Preconditions)** — стан системи перед тестом
- **Кроки (Steps)** — послідовність дій
- **Очікуваний результат (Expected Result)** — що повинно статися
- **Фактичний результат (Actual Result)** — що насправді сталося

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md` — "Тест-кейс – це тестовий артефакт, суть якого полягає у виконанні деякої кількості дій та/або умов..."

**Приклад:**
```
Тест-кейс: Перевірка входу з неправильним паролем

Передумови:
- Користувач на сторінці входу
- Облікаючий запис існує

Кроки:
1. Ввести email
2. Ввести неправильний пароль
3. Натиснути кнопку "Вхід"

Очікуваний результат:
- Відображається повідомлення про помилку "Неправильний пароль"
- Користувач залишається на сторінці входу
```

### Test Scenario / Сценарій тестування

**Англійська:** Test Scenario
**Українська:** Сценарій тестування (або: тестовий сценарій)

**Розрізнення від тестового випадку:**
- **Тестовий випадок** — одна окремена ситуація
- **Сценарій** — кілька ситуацій у логічній послідовності

```
Тестовий випадок 3: Вихід з облікового запису
```

## Терміни щодо рівнів тестування

### Test Level / Рівень тестування

**Англійська:** Test Level
**Українська:** Рівень тестування

**Визначення:**
> Категорія тестування, що визначається архітектурним рівнем системи, який тестується. Рівні тестування відповідають етапам розробки та розгортання.

**Основні рівні:**
1. **Модульне тестування (Unit Testing)** — тестування окремих модулів/функцій
2. **Інтеграційне тестування (Integration Testing)** — тестування взаємодії модулів
3. **Системне тестування (System Testing)** — тестування всієї системи
4. **Приймальне тестування (Acceptance Testing)** — тестування з точки зору користувача

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`
- `dataset/articles/qalight/parsed/rivni-testuvannia/`

---

### Test Type / Тип тестування

**Англійська:** Test Type
**Українська:** Тип тестування

**Визначення:**
> Категорія тестування, що визначається цільми та методами перевірки. На відміну від рівнів, типи не прив'язані до архітектури системи.

**Основні типи:**
1. **Функціональне тестування (Functional Testing)** — перевірка функціональності
2. **Нефункціональне тестування (Non-functional Testing)** — перевірка властивостей (продуктивність, безпека, надійність)
3. **Регресійне тестування (Regression Testing)** — перевірка після змін
4. **Дим-тестування (Smoke Testing)** — базова перевірка
5. **Санітарне тестування (Sanity Testing)** — визначена функція працює

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`
- `dataset/articles/qalight/parsed/vidi-testuvannia/`

### Test Technique / Техніка тестування

**Англійська:** Test Technique
**Українська:** Техніка тестування (або: метод тестування)

**Визначення:**
> Конкретний метод або підхід до розробки тестових випадків. Техніки тестування спеціалізуються на виборі тестових даних та створенні тест-кейсів.

**Основні техніки:**
1. **Еквівалентне розділення (Equivalence Partitioning)** — поділ на групи еквівалентних значень
2. **Аналіз граничних значень (Boundary Value Analysis)** — тестування на межах
3. **Таблиця прийняття рішень (Decision Table Testing)** — тестування за таблицями
4. **Тестування переходів станів (State-Transition Testing)** — тестування переходів

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`

### Test Condition / Умова тестування

**Англійська:** Test Condition
**Українська:** Умова тестування

**Визначення:**
> Окремий аспект або вимога системи, яка повинна бути перевірена. Одна умова тестування може охоплюватися кількома тестовими випадками.

**Приклад:**
- Умова: "Форма приймає тільки числові значення у полі 'Вік'"
- Тестові випадки: "Ввести буквене значення", "Ввести спеціальні символи", "Ввести число 150"

### Test Basis / База тестування

**Англійська:** Test Basis
**Українська:** База тестування (або: основа тестування)

**Визначення:**
> Документи, вимоги та специфікації, на основі яких створюються тестові випадки. База тестування — це "джерело істини" для того, що потрібно тестувати.

**Приклади бази тестування:**
- Бізнес-вимоги (Business Requirements Document)
- Технічні вимоги (Technical Requirements)
- Специфікація системи (System Specification)
- Документація користувача (User Documentation)
- Дизайн-документи (Design Documents)

## Терміни щодо білого та чорного ящику

### White Box Testing / Тестування білого ящику

**Англійська:** White Box Testing (також: Structural Testing, Glass Box Testing)
**Українська:** Тестування білого ящика (або: структурне тестування)

**Визначення:**
> Тип тестування, при якому тестувальник має доступ до вихідного коду системи та розуміє її внутрішню логіку. Тестування спрямоване на перевірку внутрішніх структур та потоків виконання.

**Характеристики:**
- Тестувальник бачить код
- Фокус на внутрішніх путях виконання
- Використовуються керуючі графи (Control Flow Graphs)
- Вимагає глибокого розуміння архітектури

**Техніки білого ящику:**
- Statement Coverage (покриття операторів)
- Branch Coverage (покриття гілок)
- Condition Coverage (покриття умов)
- Path Coverage (покриття путей)

**Джерела:**
- `dataset/articles/qalight/parsed/tipi-testuvannia/white-black-grey-box-testuvannia.md`
- `dataset/books_pdf/parsed/Copeland_2004_SoftwareTestDesign.md` (Chapter 10)

---

### Black Box Testing / Тестування чорного ящику

**Англійська:** Black Box Testing (також: Functional Testing)
**Українська:** Тестування чорного ящику (або: функціональне тестування)

**Визначення:**
> Тип тестування, при якому тестувальник не має доступу до вихідного коду та не знає внутрішньої логіки системи. Тестування спрямоване на перевірку зовнішньої поведінки та функціональності.

**Характеристики:**
- Тестувальник не бачить код
- Фокус на вхідні дані та вихідні результати
- Тестування відповідності вимогам
- Не потребує глибокого розуміння архітектури

**Техніки чорного ящику:**
- Еквівалентне розділення
- Аналіз граничних значень
- Таблиця прийняття рішень
- Тестування переходів станів

**Джерела:**
- `dataset/articles/qalight/parsed/tipi-testuvannia/white-black-grey-box-testuvannia.md`
- `dataset/books_pdf/parsed/Copeland_2004_SoftwareTestDesign.md` (Розділи 3-9)

---

### Grey Box Testing / Тестування сірого ящику

**Англійська:** Grey Box Testing (також: Glass Box Testing)
**Українська:** Тестування сірого ящику

**Визначення:**
> Гібридний тип тестування, при якому тестувальник має частковий доступ до вихідного коду та деяке розуміння внутрішньої логіки системи, але не повне.

**Характеристики:**
- Тестувальник частково бачить код
- Комбінація техніки білого та чорного ящику
- Часто використовується в інтеграційному тестуванні
- Баланс між технічним розумінням та фокусом на функціональність

**Джерела:**
- `dataset/articles/qalight/parsed/tipi-testuvannia/white-black-grey-box-testuvannia.md`

## Терміни щодо звітування та управління

### Bug Report / Баг-репорт

**Англійська:** Bug Report (також: Defect Report)
**Українська:** Баг-репорт (або: звіт про дефект)

**Визначення:**
> Технічний документ, який містить повний опис виявленого дефекту, включаючи інформацію про дефект, умови його виникнення, кроки для відтворення, очікуваний та фактичний результати.

**Обов'язкові поля:**
- Однозначна назва
- Опис проблеми
- Кроки для відтворення
- Очікуваний результат
- Фактичний результат
- Серйозність (Severity)
- Пріоритет (Priority)
- Середовище та конфігурація

**Джерела:**
- `dataset/articles/qalight/parsed/osnovi/slovnik-testuvalnika.md`
- `dataset/articles/qalight/parsed/testovi-artefakti/bug-report-zvit-pro-pomilku.md`

### Severity / Серйозність

**Англійська:** Severity
**Українська:** Серйозність (або: строгість)

**Визначення:**
> Ступінь впливу дефекта на працездатність системи. Серйозність визначається технічним впливом дефекту.

**Рівні серйозності:**
1. **Critical** — система повністю неробоча
2. **High** — важлива функція неробоча
3. **Medium** — функція частково неробоча
4. **Low** — незначна проблема, косметична

### Priority / Пріоритет

## Терміни щодо методологій розробки (розширено)

### LEAN / Бережливість

**Англійська:** LEAN (часто: Lean Software Development)
**Українська:** Бережливість / Бережлива розробка

**Визначення:**
> Підхід до розробки ПЗ, заснований на концепції бережливого виробництва (Lean Manufacturing). Метою LEAN є мінімізація витрат та часу розробки шляхом усунення всього, що не додає цінності продукту.

**Основні принципи LEAN:**
1. **Визначення цінності** (Identify Value) — розуміння того, що цінне для клієнта
2. **Картування потоку цінності** (Map Value Stream) — визначення кроків розробки
3. **Створення потоку** (Create Flow) — забезпечення безперервного потоку робіт
4. **Встановлення pull** (Establish Pull) — розробка за попитом, а не за пропозицією
5. **Прагнення до досконалості** (Pursue Perfection) — постійне поліпшення процесу

**Ключові концепції LEAN:**
- **Muda (Мьюда)** — марнування, діяльність, яка не додає цінності
- **Kanban** — система управління потоком робіт (дошка Kanban з картками)
- **Just-in-Time (JIT)** — розробка саме того, що потрібно, саме тоді, коли потрібно
- **Mura (Мура)** — нерівномірність, варіабельність процесу
- **Muri (Мурі)** — перевантаження людей або обладнання

**Як LEAN використовується в тестуванні:**
- Ранній пошук дефектів (дешевше виправляти на ранніх етапах)
- Тестування лише критичних функцій спочатку
- Скорочення документації до мінімально необхідної
- Паралельна розробка та тестування (не послідовно)
- Усунення зайвих тест-кейсів, що не додають цінності

**Різниця від Agile:**
| LEAN | Agile |
|---|---|
| Фокус на виключенні мусора | Фокус на людях та колаборації |
| Мінімізація витрат | Адаптація до змін |
| Потоковий підхід (Kanban) | Ітеративний підхід (Scrum) |
| Запозичено з виробництва | Власна філософія розробки |

**LEAN та Kanban:**
Kanban часто пов'язується з LEAN. Kanban — це система управління потоком робіт за допомогою дошки з трьома колонками: "To Do" (Зробити), "In Progress" (Робиться), "Done" (Зроблено).

- `dataset/articles/QA_Bible/sdlc-i-stlc/agile.md` — "Бережливая разработка программного обеспечения использует подходы из концепции бережливого производства"

### Kanban / Канбан

**Англійська:** Kanban
**Українська:** Канбан

**Визначення:**
> Візуальна система управління потоком робіт, заснована на LEAN-принципах. Канбан використовує дошку з картками для відстеження статусу завдань та обмеження обсягу роботи одночасно (WIP — Work In Progress).

**Компоненти Kanban:**
1. **Дошка Kanban** — фізична або цифрова дошка з колонками
2. **Картки** — представлення окремого завдання
3. **WIP Limit** — максимальна кількість завдань в одній колонці одночасно
4. **Flow** — плавне переміщення завдань по колонках

**Структура Kanban-дошки:**
```
To Do (Зробити) | In Progress (Робиться) | Done (Зроблено)
WIP Limit: ∞    | WIP Limit: 5           | WIP Limit: ∞
```

**Переваги Kanban:**
- Ясна видимість всіх робіт
- Скорочення часу виконання (Lead Time)
- Гнучкість у приоритизації
- Запобігання перевантаженню команди

**Канбан vs Scrum:**
| Kanban | Scrum |
|---|---|
| Неперервний потік | Ітеративні спринти |
| Змінна довжина цикла | Фіксована довжина спринту (2-4 тижні) |
| Змінна команда розміру | Фіксована команда розміру |
| Гнучка пріоритизація | Фіксована мета спринту |

**Джерела:**

## Правила використання термінів у посібнику

1. **Послідовність:** Один й той самий термін завжди перекладається однаково
2. **Першоджерела:** Визначення берються з `dataset/`
3. **Розрізняння:** Критичні терміни (Error/Defect/Failure) завжди розрізняються
4. **Префікси:**
   - Англійський термін наводиться першим
   - Українська назва наводиться другою
   - Синоніми вказуються у дужках

5. **При першому введенні терміна:**
   - Наводиться його назва (англ. + укр.)
   - Надається визначення
   - За необхідності — пояснення розрізнення від подібних термінів
   - Далі можна використовувати скорочені версії або тільки українською
