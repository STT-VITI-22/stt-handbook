
# Історія роботи над проектом (Work History)

## Глобальна ціль
Створення якісного датасету (Markdown) з PDF/DOC/веб-сторінок для подальшого використання (LLM, RAG). Поточний етап: конвертація технічного підручника з тестування ПЗ (`testyvan.pdf`).

## Пройдений шлях та результати

### 1. Парсинг веб-сторінок (База знань QALight)
- **Спробували:** `httpx` + `BeautifulSoup4` + `markdownify`.
- **Статус:** Успішно. Визначено як оптимальний стек для HTML (швидко, модульно). Зображення витягуються локально.

### 2. Парсинг PDF: Спроба 1 (PyMuPDF4LLM)
- **Спробували:** Швидкий парсинг за допомогою легкої бібліотеки `pymupdf4llm` (скрипт `pymupdf4llm_script.py`).
- **Кінцевий фейл (Чому відмовились):** Абсолютна непридатність для складних підручників. Втрата математичних символів (знищення логіки формул), знищення структури таблиць, злиття абзаців і списків, відсутність екстракції зображень/діаграм.

### 3. Парсинг PDF: Спроба 2 (Gemini API / VLM)
- **Спробували:** Використати Vision-моделі Gemini для конвертації сторінок в Markdown (скрипти `gemini_hybrid_pipeline.py`, `local_vlm_script.py`).
- **Кінцевий фейл (Чому відмовились):** Хоча якість розпізнавання формул та коду була ідеальною, ми зіткнулися з жорсткими обмеженнями API (`429 RESOURCE_EXHAUSTED` / `Quota Exceeded`). Безкоштовний ліміт (15 RPM / 20 сторінок на день) не дозволяє обробити 300-сторінкову книгу без створення ферми ключів або платної підписки.

### 4. Парсинг PDF: Спроба 3 (Docling та Marker)
- **Спробували:** Запустити в Colab `docling` (через `docling_extractor.py`) та `marker-pdf` (через `marker_script.py` / зошит).
- **Кінцевий фейл (Чому відмовились спочатку):**
  - **Marker:** Впав з помилкою `SpawnError: docker binary not found`. Бібліотека `surya-ocr` для vLLM бекенду потребувала Docker, якого немає в Colab.
  - **Docling:** Впав з помилкою `RuntimeError: Failed to load image processor... Could not import module 'AutoImageProcessor'`.
- **Повторна спроба (Marker v0.2.8):** Вирішили повернутися до Marker через потребу у формулах. Відкотилися на версію `0.2.8` (без Docker), але зіткнулися з dependency hell:
  - `surya-ocr` без `segformer` (вирішено фіксацією версії `0.4.14`).
  - `KeyError: 'sdpa'` (вирішено написанням Python-патчу, який додає підтримку 'sdpa' у файл `surya/model/ordering/decoder.py` на льоту).
- **Статус:** Очікуємо результатів виконання запатченого `marker_colab_runner.py`.

### 5. Парсинг PDF: Спроба 4 (MinerU / Magic-PDF)
- **Спробували:** Побудувати пайплайн в Google Colab на базі MinerU (`magic-pdf`).
- **Проблеми та їх вирішення:**
  - *Проблема:* Галюцинації (генерування сміття типу `$ segmentaloperators...`). *Причина:* Модель формул `UniMERNet` хибно спрацьовувала. *Вирішення:* Вимкнули розпізнавання формул у конфігу.
  - *Проблема:* Помилка OCR та кракозябри на українському тексті. *Причина:* Видалені кириличні ваги в репозиторії. *Вирішення:* Додали примусове завантаження `cyrillic_PP-OCRv3_rec_infer.pth` та `--lang uk`. Основний текст почав розпізнаватися ідеально.
- **Кінцевий фейл Magic-PDF (Чому відмовились):**
  - Не розпізнає **блоки коду**: втрачаються відступи, код зліплюється в абзаци (критично для підручника).
  - Втрата **формул**: через вимкнену модель математика не парситься.
  - Збої на **діаграмах**: OCR намагається читати текст на картинках і видає сміття.
- **Статус інструменту:** Відхилено для складних підручників.

## Поточний статус (Що робимо далі)
Оскільки є доступ до Colab (GPU T4), прийнято рішення відмовитися від `magic-pdf` і переключитися на більш потужні інструменти для складної верстки: **Marker** (Surya OCR) або **Docling** (IBM). Вони краще зберігають код і математику.

### Спроба 7 (OOM Crash & max_pages)
**Інструмент:** marker-pdf 0.2.8
**Опис:** Всі патчі були успішно застосовані (models/eager та pdftext/PdfDocument). Моделі завантажились у пам'ять, але під час конвертації Colab завис на 20 хвилин і ядро "мовчки" перезавантажилося.
**Результат:** Фейл (OOM killer).
**Причина:** При `--max_pages 500` marker-pdf (стара версія) перетворює всі сторінки на зображення і тримає їх у System RAM. Це перевищило ліміт безкоштовного Colab (12.7 ГБ) і процес був примусово вбитий Linux.
**Що змінено:** У скрипт `marker_colab_runner.py` додано ліміт `--max_pages 20`, щоб перевірити стабільність на меншому обсязі та обійти OOM. 
**Результат 2:** Скрипт успішно згенерував `testyvan-01.md`.
**Висновки щодо отриманого markdown (перші 20 сторінок):**
- Зміст перетворився на Markdown-таблицю (візуальні моделі плутають крапки-заповнювачі зі стовпцями). Для LLM це прийнятно.
- **Наступний крок:** створено окремий файл `tools/deprecated_pdf_parsers/colab/marker_complex_pages_tester.py`, який за допомогою `pypdf` вирізає складні сторінки з середини (112-135) і пропускає їх через Marker для оцінки якості розпізнавання коду та графіки.

### 6. Парсинг PDF: Спроба 5 (Повернення до Gemini 1.5 Flash)
- **Причина відмови від Marker:** Після тестування `marker-pdf==0.2.8` на складних сторінках виявлено критичні вади: модель `surya-layout` шматує блок-схеми на незв'язні картинки, а також **повністю знищує форматування коду** (зліплює C++ код в один рядок без відступів та блоків ` ``` `). Для підручника це неприпустимо. Встановити новіші версії Marker у Colab неможливо через жорстку залежність від Docker (vLLM).
- **Вирішення проблеми з моделями (404):** Скрипт оновлено функцією `get_working_flash_model()`, яка динамічно тестує доступні моделі, обходячи обмеження на `gemini-2.5-flash` для нових акаунтів і вибираючи робочу (напр., `gemini-3.5-flash`).
- **Обхід фільтру:** Створено скрипт `tools/extract_missing.py` на базі `pymupdf4llm` для витягування сирого тексту. Оскільки `pymupdf4llm` зліпив блоки коду в один рядок, форматування для цих 7 сторінок було ідеально відновлено вручну і збережено у `dataset/books_pdf/gemini/missing_pages_perfect.md` для фінальної склейки.
- **Гібридне витягування візуалу:** Скрипт `gemini_pdf_parser.py` оновлено. Тепер він автоматично витягує всі растрові картинки (PyMuPDF) у папку `images/`, а для векторних блок-схем генерує Mermaid.js код. У промпт додано жорсткі інструкції уникати дублювання та генерувати детальний alt-text для зображень (для потреб RAG).
- **Супер-відмовостійка паралельна обробка:** Для обходу лімітів та прискорення парсингу скрипт переписано на `google-genai` SDK з використанням `threading` та `Queue`. 
  - Реалізовано "розумний" rate-limiting (затримка лише якщо запит тривав менше 4.1с).
  - Створено локальну БД `api_usage.json` для трекінгу квот (500 RPD для `gemini-3.5-flash-lite`).
  - При виявленні "мертвого" ключа (квота 0) або 429-лімітів, скрипт автоматично повертає сторінку в загальну чергу для обробки іншим робочим ключем.
  - Успішний стрес-тест: повноцінна книга розпізнана за ~14 хвилин (894.3 сек).
- **Інцидент із зображеннями (Сміття vs Користь):** PyMuPDF витягував АБСОЛЮТНО всі графічні елементи (включно з іконками та лініями), що призвело до створення папки `images/` на 27+ тисяч файлів. Через це користувач видалив всю папку `Gregory_2014` (Криспин), випадково втративши й корисні ілюстрації. Щоб цього більше не сталось, у `gemini_pdf_parser.py` впроваджено фільтр: зберігаються лише зображення з шириною та висотою >= 100 пікселів.

### 7. Архітектурний рефакторинг та вирішення проблеми фрагментації (Модульний парсер)
- **Проблема (Spaghetti Code):** Старі монолітні скрипти обробляли презентації (PPTX) по одному слайду ізольовано. Це призводило до втрати контексту (Gemini не знала, що слайд є продовженням теми), дублювання заголовків (`# Спіральна модель` на кожному слайді), галюцинацій зображень та дублювання малюнків у Mermaid. Також багатопотоковість викликала DDoS API через баги у `while`-циклах. Файлова система `dataset/` була хаотичною (`books_pdf/lectures`, `books_pdf/gemini` тощо).
- **Рішення (Pipeline Architecture):** Парсери повністю переписані на модульну архітектуру (`tools/doc_parser/`):
  1. **Extractor** (`pptx_extractor.py`): Витягує слайди. Динамічно знаходить і ігнорує логотипи/водяні знаки (картинки, що є на >20% слайдів). Евристично визначає заголовок кожного слайду.
  2. **Chunker** (`core/chunker.py`): Семантично групує послідовні слайди з однаковим заголовком в один логічний блок (Chunk) і збирає лише унікальні картинки за їхнім хешем.
  3. **Generator** (`generators/llm_generator.py`): Відправляє готовий Chunk у Gemini з суворою вказівкою НЕ малювати Mermaid, якщо блок-схема вже є на фото (передаємо картинки прямо як мультимодальний контекст).
  4. **Orchestrator** (`parse_docs.py`): Використовує надійний `ThreadPoolExecutor` замість сирих `Queue` (без Race Conditions), має безпечний для потоків JSON-обліковець лімітів із щоденним скиданням та зручний `tqdm` інтерфейс.
- **Нормалізація Датасету:** Реструктуризовано папку `dataset/`. Тепер усі файли поділено на категорії за доменами (`books_pdf`, `pptx`, `dou`, `qalight`), кожна з яких має сувору структуру `raw/` (для вихідних файлів) та `parsed/` (для Markdown). Старі скрипти перенесено до `tools/legacy/`, а веб-парсери ізольовано у `tools/web_scrapers/`.

### Ітерація 4 (Виправлення логічних розривів та форматування OCR)
- **Проблема 1:** `SlideChunker` розривав логічні блоки, якщо слайд-продовження не мав заголовка або мав опечатку OCR (напр. "Принцирі"). В результаті створювались осиротілі чанки, для яких LLM галюцинувала вигадані заголовки (напр. "Каскадна модель" замість ітеративної).
- **Рішення 1:** Додано Fuzzy Matching (difflib, схожість > 80%) та умову `elif not slide.title` у `chunker.py`. Тепер слайди без заголовків жорстко пришиваються до попередньої теми.
- **Проблема 2:** При злитті слайдів втрачалась нумерація списків (цифри 5-8 губились або перетворювались на маркери `-`), дублювались головні заголовки (`## Принципи тестування` виводилось двічі), і губились підзаголовки (напр. "Bug Reporting board").
- **Рішення 2:** Кардинально оновлено `PROMPT_TEMPLATE`. Введено правила: "Уникай дублювання заголовків", "ОБОВ'ЯЗКОВО збережи наскрізну нумерацію (5, 6, 7, 8)", "Всі інші підзаголовки форматуй як `### Підзаголовок`". Заборонено галюцинувати чужі заголовки.

### Ітерація 5 (Підводні камені OCR та регресії)
- **Проблема 1 (Регресія списків):** Намагаючись навчити модель зберігати наскрізну нумерацію (5, 6, 7, 8), з промпту випадково випало правило про розривання зліплених списків (`• Пункт 1 • Пункт 2`). Через це марковані списки знову перетворилися на абзаци тексту.
- **Рішення 1:** Повернуто жорстке правило розгортання зліплених маркерів у багаторядковий Markdown-список.
- **Проблема 2 (Причина дублювання заголовків):** Навіть після оновлення `chunker.py` заголовки "Принципи тестування" продовжували розриватися і дублюватися. Виявилося, що алгоритм визначення заголовків у `PPTXExtractor` брав *абсолютно найбільший шрифт* на сторінці. Оскільки цифри в діаграмі (5, 6, 7, 8) були більші за шрифт заголовка, скрипт вважав цифру "5" заголовком і відмовлявся склеювати слайди.
- **Рішення 2:** Алгоритм `_extract_title` додатково скориговано. Зону пошуку найбільшого шрифту звужено до верхніх 15% екрану (`y0 < page_height * 0.15`). Попереднє значення (35%) виявилося завеликим, оскільки елементи схем з великим шрифтом (наприклад, номери або заголовки блоків) іноді потрапляли в цю зону і хибно розпізнавались як заголовок слайда.
- **Проблема 3 (Прив'язка ілюстрацій):** На складних слайдах з кількома схемами LLM вставляла картинки хаотично або переплутувала їх місцями (наприклад, ставила просту схему під заголовком "Плоска модель"). Це відбувалося через те, що модель бачила лише вирізані картинки і сирий текст, тому їй доводилось "вгадувати" відповідність між текстом і картинкою виключно за порядком або їхнім вмістом, не маючи реального візуального контексту розташування елементів на слайді.
- **Рішення 3:** Змінено формат передачі контексту в `LLMGenerator`. По-перше, застосовується інтерлівінг: шлях до картинки `[ЗОБРАЖЕННЯ: шлях]` вставляється безпосередньо перед об'єктом зображення. По-друге, в `PPTXExtractor` додано створення скріншоту всього слайда (`page_N_full.jpeg`), який передається в LLM з позначкою "ВІЗУАЛЬНИЙ КОНТЕКСТ СЛАЙДУ". Це дозволяє моделі підглядати на оригінальне розташування схем відносно тексту і безпомилково розставляти вирізані ілюстрації в Markdown.
- **Проблема 4 (Дублювання таблиць і тексту):** Після передачі "ВІЗУАЛЬНОГО КОНТЕКСТУ СЛАЙДУ", мультимодальна модель почала виконувати OCR цього контекстного зображення. Через це вона дублювала таблиці та текст: спочатку виводила таблицю-картинку (або абзац з тексту), а потім намагалася відтворити її заново з `СИРОГО ТЕКСТУ`, вставляючи гібридні LaTeX-шматки.
- **Рішення 4:** У `PROMPT_TEMPLATE` додано чітке розмежування: суворо заборонено транскрибувати (переписувати) текст із зображень "контексту" в тіло документа. Єдиним джерелом тексту є `СИРИЙ ТЕКСТ РОЗДІЛУ`. Проте, дозволено читати текст із "вирізаних ілюстрацій" виключно для формування короткого опису (`alt-text`) до них.
- **Проблема 5 (Вставка гербів та логотипів):** На титульних слайдах модель почала вставляти величезні герби інституту. Це сталося через те, що під час попереднього рефакторингу промпту (додавання контекстних зображень) випадково загубилося правило, яке жорстко забороняло вставляти емблеми. Крім того, герб з першого слайду не фільтрувався `PPTXExtractor`, оскільки він не повторювався на інших слайдах (count=1), тому не вважався "глобальним водяним знаком".
- **Рішення 5:** У `PROMPT_TEMPLATE` (пункт 6.Б) повернуто та посилено сувору заборону: "КАТЕГОРИЧНО ЗАБОРОНЕНО вставляти в Markdown герби, емблеми, логотипи інститутів... Їх просто ігноруй".
- **Проблема 6 (Сирі текстові теги замість картинок):** Після переписувань промпту модель почала виводити сирий текстовий тег `[ЗОБРАЖЕННЯ: шлях]` прямо в Markdown замість правильного вставляння самої картинки (наприклад `![Опис](шлях)`). Це сталося через те, що інструкція стала занадто розмитою ("встав її рівно в те місце...").
- **Рішення 6:** У пункт 6.Б додано жорстку вказівку формату: "ОБОВ'ЯЗКОВО використовуючи Markdown-формат: `![Опис](шлях)`. НІКОЛИ не виводь сирий текст `[ЗОБРАЖЕННЯ: шлях]`".
- **Проблема 7 (Переплутана структура списків та переписування тексту з картинок):** Модель вивела переплутаний ієрархічний список для стандарту ISO 25010 ("моделі якості для аудитів" стали заголовком), оскільки `PyMuPDF` витягнув текстові блоки слайду у хаотичному порядку. Модель не використала фото слайду для відновлення порядку, оскільки попереднє правило (4) занадто жорстко забороняло їй використовувати фото для роботи з текстом. Також модель продовжувала переписувати параграфи тексту з картинок (Матриця відстеження) у Markdown, дублюючи їх.
- **Рішення 7:** Оновлено пункти 6.А та 6.Б. В 6.А явно дозволено використовувати фото слайду для того, щоб зрозуміти "ЯКИЙ ПРАВИЛЬНИЙ ПОРЯДОК ТЕКСТУ, заголовків і списків", але залишено заборону на OCR. В 6.Б додано жорстку вимогу: "Якщо всередині ілюстрації є текст, ЗАБОРОНЕНО транскрибувати його в Markdown! Просто встав картинку".
- **Проблема 8 (Страх моделі переставляти рядки):** Навіть після дозволу дивитися на візуальний контекст, модель не змогла повністю зібрати переплутаний список (ISO 25010) докупи. Вона залишала деякі пункти висіти в повітрі, оскільки базове правило "перенесений слово в слово" змушувало її боятися порушувати сирий порядок рядків.
- **Рішення 8:** Додано прямий, агресивний наказ у базові правила (після виправлення опечаток): "НАЙГОЛОВНІШЕ: Якщо в `СИРОМУ ТЕКСТІ` порядок рядків переплутаний... ТИ ЗОБОВ'ЯЗАНИЙ переставити їх місцями, орієнтуючись на ВІЗУАЛЬНИЙ КОНТЕКСТ СЛАЙДУ! Відтвори правильну логічну структуру та ієрархію (як на фото)".
- **Проблема 9 (Вперте дублювання абзаців з картинок):** Оскільки текст "Матриці відстеження" був фізично вшитий в саму картинку, його не було в `СИРОМУ ТЕКСТІ`. Проте модель, маючи дозвіл "читати картинки для alt-text", читала цілі абзаци з картинки і виводила їх у Markdown, створюючи дубляж. Під час першої спроби виправити це розробник випадково затер частину правил фільтрації сміття.
- **Рішення 9:** Обережно оновлено Правило 11: додано АБСОЛЮТНУ заборону виводити в Markdown будь-які абзаци/речення, яких немає у сирому блоці тексту (окрім alt-text). У пункт 6.Б додано уточнення, що заборонено дублювати абзаци з ілюстрацій. Усі правила фільтрації збережено.
- **Проблема 10 (Списки та таблиці жахливо переплутані):** На слайді з великою таблицею (Модель якості продукту) текст зчитувався хаотично, оскільки PyMuPDF `get_text("text")` без параметрів повертає текст у порядку створення об'єктів у PowerPoint, а не візуально. LLM намагалася виправити цей хаос і розкидала пункти по колонках, виходячи з власних знань стандарту ISO.
- **Рішення 10:** У `pptx_extractor.py` під час виклику `page.get_text("text")` додано параметр `sort=True`. Тепер PyMuPDF повертає сирий текст відсортованим за фізичними координатами (згори вниз, зліва направо).
- **Проблема 11 (Зникнення заголовків на деяких слайдах):** Хоча евристичний скрипт правильно визначав заголовок слайду (напр. "ДСТУ ISO/IEC 25010..."), LLM іноді виводила його як звичайний текст, а не `## Заголовок`, оскільки заголовок ніяк явно не передавався в промпт.
- **Рішення 11:** У `llm_generator.py` додано явну ін'єкцію витягнутого `chunk.title` у текст промпту з вказівкою обов'язково використати його як `## Заголовок`.
- **Проблема 12 (Шлакові заголовки замість справжніх):** На слайді 9 ("Ролі користувачів в системі") скрипт `pptx_extractor.py` вибрав заголовком "Орієнтація на клієнта 1", оскільки цей текст мав більший шрифт (розмір 24), хоча справжній заголовок знаходився вище і мав розмір 22. Попередня логіка просто шукала абсолютний максимум шрифту у верхніх 15% екрану.
- **Рішення 12:** Удосконалено логіку `_extract_title`. Тепер скрипт знаходить всі текстові блоки з "великим" шрифтом (у межах 4pt від глобального максимуму на слайді), а потім серед них обирає той блок, який знаходиться **найвище** (має найменший `y0`).
- **Проблема 13 (Викривлення тексту на останньому слайді):** LLM правильно відфільтрувала "невидиме" сміття (приховані буліти, які витягнув PyMuPDF), але під час цього вирішила "причесати" текст, зливши два окремих речення в одне за допомогою слів "та", "замінивши". Це порушило вимогу сухої екстракції.
- **Рішення 13:** У Правило 11 додано жорстку заборону зливати окремі речення чи абзаци в одне довге речення (навіть після видалення сміття між ними). Модель зобов'язана зберігати оригінальну розбивку на речення.
- **Проблема 14 (Залишки сміття: ВІТІ, ЗСУ):** Модель не видаляла назву університету та відомства з титульного слайду, оскільки вважала їх основним "корисним" текстом сторінки, адже крім них і назви лекції там нічого немає.
- **Рішення 14:** Оновлено Правило 5: чітко вказано видаляти ці інституційні назви (ВІТІ, ЗСУ) **НАВІТЬ ЯКЩО** вони є головним текстом на титульному слайді.
- **Проблема 15 (Вигадування типів занять в назві файлів):** Функція `get_smart_filename` використовувала Gemini, щоб придумати "розумну" англійську назву файлу на базі перших двох слайдів. Через це оригінальний файл `ГЗ 1.3 ТТПЗ` (Групове Заняття) був перейменований на `lecture_1_3_ttpz` (Лекція), бо модель "зробила висновок", що це лекція, і проігнорувала справжню назву файлу.

- **Проблема 16 (Зайві скріншоти забивають диск):** Скріншоти цілих сторінок (`*_full.jpeg`), які генерувалися суто як візуальний контекст для LLM, залишалися в папках `images` після завершення роботи, засмічуючи диск і репозиторій.
- **Рішення 16:** У `parse_docs.py` додано етап автоматичного очищення (`glob`). Тепер після збереження фінального Markdown-файлу скрипт видаляє всі `*_full.jpeg` з папки, залишаючи там лише корисні вирізані ілюстрації. Старі скріншоти очищені.

### Ітерація 6 (Міграція PDF парсера)
- **Проблема 17 (Деградація PDF-парсера):** Старий `legacy/gemini_pdf_parser.py` витягував тисячі "невидимих" картинок (тіні, рамки, точки) через використання `get_images()`. Крім того, він працював суто посторінково, що розривало речення і контекст, спричиняючи дублювання тексту.
- **Рішення 17:** Створено новий модуль `tools/doc_parser/extractors/pdf_extractor.py`. Він працює через блоковий аналіз `page.get_text("dict")`, що дозволяє витягувати ЛИШЕ відрендерені картинки (ігноруючи системні тіні) з фільтрацією по площі (> 25000 px). Також він розпізнає заголовки, що дозволяє модулю `SlideChunker` склеювати сторінки в єдині логічні розділи, запобігаючи розриву речень. Оновлено `parse_docs.py` для обробки `--type pdf` через новий модуль. (Старий скрипт залишено в `legacy` для історії).
- **Проблема 18 (Склеювання 300 сторінок в один запит):** Якщо в книзі немає великих заголовків (звичайний суцільний текст), `pdf_extractor` не знаходив заголовків, і `SlideChunker` помилково вважав усі 321 сторінку одним суцільним розділом. Це призводило до спроби надіслати >300 зображень та сторінок в одному запиті до Gemini, що викликало перевантаження і повернення порожньої відповіді.
- **Рішення 18:** У `SlideChunker` (файл `core/chunker.py`) додано параметр `max_pages_per_chunk=15`. Тепер великі книги без заголовків автоматично "ріжуться" на чанки максимум по 15 сторінок.
- **Проблема 19 (NoneType object has no attribute 'strip'):** Коли Gemini не могла обробити такий гігантський запит (або через ліміт, або через safety-фільтри), вона повертала `response` без тексту (`response.text = None`). Скрипт падав з помилкою `NoneType...`.
- **Рішення 19:** У `core/gemini_client.py` додано перевірку на `response.text is None` з викиданням зрозумілої винятку, що вказує на ліміти або фільтри.
- **Проблема 20 (Скановані книги без текстового шару дають порожній результат):** Новий модульний парсер суворо забороняв LLM розпізнавати (OCR) текст з фотографій, щоб уникнути дублювання. Але для старих відсканованих книг (де немає вшитого тексту) це означало, що скрипт взагалі не витягував нічого.
- **Рішення 20:** У `generators/llm_generator.py` додано динамічне перемикання (Fallback). Якщо сумарна довжина сирого тексту в чанку < 50 символів (це точно скан), скрипт автоматично перемикається на `OCR_PROMPT_TEMPLATE`, який дозволяє і вимагає від Gemini розпізнати весь текст з картинок.
- **Проблема 21 (Провал нового PDF-парсера на реальних книгах):** Незважаючи на всі фікси, новий парсер видав жахливий результат на книзі Бейзера. Обмеження в 5 сторінок повністю знищило ідею семантичного чанкінгу, повернувши проблему розриву тексту. Блоковий аналіз `dict` губив діаграми та порушував порядок читання. Перевантаження LLM усім цим призводило до галюцинацій та втрати форматування.
- **Рішення 21:** Прийнято рішення **призупинити** розробку нового PDF-парсера і тимчасово повернутися до `legacy/gemini_pdf_parser.py` для книг. Детальний, глибокий та критичний розбір архітектурних помилок нового парсера збережено у файл `local-dev/pdf_parser_critical_analysis.md`. Пріоритет переведено на парсинг веб-сайтів (DOU, QALight).
