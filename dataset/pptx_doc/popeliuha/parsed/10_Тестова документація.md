# Основні терміни з ISTQB

* **Test basis:** Документ, на основі якого визначаються вимоги до системи і на якому базуються тест кейси.
* **Testware:** Артефакти, створені в процесі тестування і необхідні для планування, розробки і виконання тестів. Наприклад: документація, сценарії, очікувані результати, процедури установки і видалення, файли, бази даних, середовище і будь-яке ПЗ, що використовуються в тестуванні.
* **Test environment:** Середовище, що включає апаратне забезпечення, вимірювальну апаратуру, програмний інструментарій та інші інструменти, необхідні для проведення тесту.
* **Test condition:** Об'єкт, функція чи подія в компоненті чи системі, які повинні бути перевірені тест кейсами.
* **Test data:** Дані, що існують до початку виконання теста і впливають на роботу.
* **Test harness:** Тестове середовище, готове для проведення теста. Включає test environment, test cases, test data, програму, що тестується.

# Основна тестова документація

* **Test case**: Набір вхідних значень, передумов виконання, очікуваних результатів та післяумов, розроблений для певної цілі чи test condition. [IEEE 610]
* **Test suite**: Комплект test cases для компонента чи системи, в якому зазвичай післяумова одного тесту використовується як передумова для наступного.
* **Test summary report**: Документ, що звітує висновок по задачам та результатам тестування. [IEEE 829]
* **Defect report**: Документ, що містить звіт про недолік в компоненті чи системі, який може привести компонент чи систему до неможливості виконати потрібну функцію. [IEEE 829]
* **Test plan**: Документ, що описує цілі, підходи, ресурси та графік запланованих тестових активностей. Він визначає об'єкти тестування, завдання, відповідальних за завдання, ступінь незалежності кожного тестувальника, тестове середовище, метод проектування тестів, визначає критерії входу та виходу а також будь-які ризики, що вимагають планування. [IEEE 829]
* **Test strategy**: Високорівневий опис рівнів тестування, що повинні бути виконані, і тестування, що входить в ці рівні, для організації програми із одного чи декількох проектів.
* **Test policy**: Документ високого рівня, що описує принципи, підхід та основні цілі організації в тестуванні.

*(Вся непозначена інформація - з глосарію ISTQB 2.3 (2014))*

# Check-list теорія

* Чек-ліст - табличка, яка складається з назви кроку, статусу та тестових даних або коментаря
* Назви кроку є лаконічними, зрозумілими і починаються з дієслова: “Додати користувача в друзі”
* Статуси існують наступні:
  * Passed
  * Failed
  * Blocked
  * In progress
  * Skipped
  * Not run
* В тестові дані вводимо все, що користувач обирає або вводить з клавіатури (ім’я, вік, адреси, паролі, дати, назви товару тощо)
* Чек-ліст використовується для швидкого тестування (техніки, засновані на досвіді)

# Хорошими негативними перевірками є:

* Залишати поля вводу пустими
* Вводити Пробіл в поля для вводу
* Вводити числа там, де потрібні строкові значення (Ім'я і Прізвище)
* Вводити літери там, де потрібні чисельні значення (Номер телефону)
* Вводити текст різними мовами: китайською, івритом тощо
* Вводити пробіл на початку, в середині, в кінця строки і перевірити валідацію
* Вводити SQL-ін'єкції і JS код в поля для введення.

# Test Cases теорія

* Тест кейс - це документ, що являється інструкцією тестування і включає в себе кроки для виконання тестової ситуації і очікуваний результат.
* Тест кейс - це більш детальна і формальна документація, ніж чек-ліст, і використовується частіше.
* Набір тест-кейсів називається **Test Suite**. Зазвичай тест кейси групують по темі або сторінці, яку вони тестують.

# Test Case складається з:

* **ID** - унікальний ідентифікатор тест-кейсу. Його зручно використовувати для легкого пошуку тест-кейсу.
* **Назва** - короткий опис суті перевірки. Починається з дієслова.
* **Передумови** - опис дій, які необхідно виконати перед основними кроками. Наприклад, відкрити сайт, мати зареєстрований аккаунт.
* **Кроки** - дії, які необхідно виконати для перевірки.
* **Післяумови (опціонально)** - дії, які необхідно виконати, щоб повернути систему в попередній стан. Наприклад, видалити користувача.
* **Тестові дані** - всі дані, які користувач вводить або обирає. Наприклад, Ім'я, номер телефону тощо.
* **Скріншоти** - кожен крок має включати скріншот, щоб було зрозуміло, які дії проводити.
* **Очікуваний результат** - те, що ми очікуємо побачити в результаті перевірки.
