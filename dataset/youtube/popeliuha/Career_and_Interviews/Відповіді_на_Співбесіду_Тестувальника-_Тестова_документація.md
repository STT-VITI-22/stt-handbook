# Відповіді на Співбесіду Тестувальника: Тестова документація

**Які види тестової документації ви знаєте?**
Можна назвати наступні види:
- Test case
- Check list
- Вимоги (requirements)
- Test plan
- Test strategy
- Test policy
- Test summary report (або test report, test run result)
- Bug report (звіти про дефекти).

**Що таке вимоги і які види вимог ви знаєте?**
Вимоги — це документ, в якому описується те, що має робити програма, і як вона має це робити. Вимоги допомагають пришвидшити розробку, адже з ними розробники точно знають, що їм потрібно запрограмувати. 
Види вимог:
- Software Requirement Specification (SRS).
- Product Requirement Document (PRD).
- User Stories — це окремий неформальний вид вимог, в якому описується історія з точки зору користувача. Вона складається з трьох частин: «Як такий-то користувач, я хочу, щоб відбулося таке-то, для того, щоб таке-то». Наприклад: «Як адміністратор, я хочу банити інших користувачів, які спамлять, для того, щоб вони перестали спамити в чат».
- Acceptance criteria — це ще один підвид вимог. Acceptance criteria є обов'язковими для виконання, щоб допустився реліз. Якщо acceptance criteria не виконані, релізу не буде: він або перенесеться, або команді доведеться терміново працювати для виконання всіх умов. 

**Що таке test case?**
Test case — це інструкція з тестування. Це документ, який складається з кроків для відтворення та очікуваного результату. Тестувальники пишуть test cases для того, щоб задокументувати, що саме вони перевіряють, і щоб інші тестувальники могли перевірити функціонал за такими самими кроками. 
Також у test cases можуть бути тестові дані, скріншоти, назва. Серед необов'язкових полів: пріоритет, test suite, модуль, до якого відноситься test case, та категорія (наприклад, UI, performance, functional test, regression test).

**Що таке test suite?**
Test suite — це об'єднання test cases за певною темою. Це можна уявити як папку з фотографіями: якщо є 1000 фотографій, їх розділяють на декілька папок за тематикою («День народження», «Море», «Новий рік» тощо). Так само test cases об'єднуються за певною тематикою в test suites.

**З чого складається test case?**
Test case складається з:
- ID.
- Назви (необов'язково).
- Опису.
- Pre-conditions (передумови) — дії, які потрібно виконати до основних кроків.
- Steps to reproduce (кроки відтворення).
- Expected result (очікуваний результат). 
Актуального результату в test cases немає і не може бути, тому що актуальний результат пишеться тільки в bug reports. Test case описує лише те, як система повинна працювати. 
- Скріншоти (опціонально). Іноді на проектах використовують скріншоти з реального результату або з блок-схем/мок-апів. Вони корисні, особливо зі стрілочками, щоб тестувальник швидко знайшов потрібну кнопку і ефективно попрацював. 
- Test data (тестові дані) — дані, які вводяться для тестування (наприклад: ім'я, прізвище, місто, стать, дата народження при реєстрації).
- Priority (пріоритет) — Critical, High, Medium, Low. Виставляється залежно від важливості тесту.
- Test type (тип тесту) — functional, regression, UI test тощо.
- Поля «творець» та «аудитор» (зазвичай ставляться автоматично).

**Що таке check list?**
Check list — це список, який частіше за все подається у вигляді таблиці (Excel), що складається з мінімум трьох колонок: 
- ID кроку (порядковий номер).
- Назва кроку.
- Статус: Passed (перевірка пройшла успішно), Failed (знайдено баг), Blocked (через інший баг неможливо протестувати дану функціональність), In Progress (тестується прямо зараз) або Skipped (пропущено, щоб повернутися пізніше).
Необов'язкова, але важлива колонка — тестові дані (що конкретно вводимо). Як варіант, ці тестові дані можна вводити безпосередньо в сам крок (наприклад: «Зареєструватися: ім'я Наталя, прізвище...»).

**Чим відрізняється check list від test case?**
Check list простіший, test case об'ємніший і детальніший. Check list зазвичай обирають у менших командах, де функціонал є очевидним і не потрібно розписувати детальні кроки. Також він використовується, коли немає бюджету на написання детальних test cases або на програму для керування ними (наприклад, TestRail).

**Що таке test plan?**
Test plan — це тестовий документ, який описує, як буде відбуватися процес тестування. Test plan пишеться на різні рівні:
- На рівень фічі (функціональності).
- На рівень модуля (найменшої одиниці програми).
- На рівень спринта (проміжку часу, в середньому два тижні).
- На рівень релізу.
В test plan описуються наступні пункти:
- Опис (для чого цей test plan розроблений).
- Approvals (підтвердження). Наприклад, QA розробляє test plan, а Tech Lead його перевіряє (аналог code review для документації). Якщо є зауваження, QA їх виправляє, після чого документ отримує статус Approved.
- Features to be tested та features not to be tested (що буде тестуватися, а що ні в рамках (scope) цього плану).
- Типи, рівні та техніки тестування, які будуть використовуватися.
- Roles and responsibilities (ролі та обов'язки). Наприклад, обов'язок QA Automation інженера — покривати автотестами регресійні тести, обов'язок Manual QA — створювати test cases, заводити bug reports та тестувати основний функціонал після деплою.
- Ризики та способи їх зменшення (mitigation). Наприклад, якщо частина коду ризикована, фіксується ризик виникнення багів і додається вимога перевіряти дану фічу під час кожної регресії.
- Entry та Exit criteria (критерії входу та виходу з тестування). 
  - Entry criteria (критерії входу) — те, що має бути виконано перед початком тестування (наприклад, наявність QA environment з тестовими даними та задеплоєна фіча).
  - Exit criteria (критерії виходу) — умови, за яких тестування припиняється (наприклад, протестовано 99% тестів, pass rate понад 97%, відсутні критичні баги, закриті всі заплановані таски). Також це можуть бути організаційні фактори: закінчення бюджету або настання дедлайну релізу.
- Test deliverables — усе, що створюється в процесі тестування (тестові артефакти, test cases, автотести, згенеровані та ручні test reports).
- Schedule (графік) — періоди тестування конкретних фічей та виконання тасок.
- Пріоритети.
- Staffing and training needs (потреби в персоналі та навчанні) — матеріали, відео та інструкції, потрібні для онбордингу та початку тестування.
- Environments (середовища), на яких планується тестування. Наприклад, QA (першочергове тестування свіжих фічей, найбільш prod-like), Staging, на який можуть заливати hotfixes (швидкі фікси, які треба протестувати терміново).
- Операційні системи, браузери та девайси.

**Чим test plan відрізняється від test strategy?**
Згідно зі стандартом ISO/IEC/IEEE 29119-3:
- Test plan — документ, який описує тестування на рівні продукту: релізу, спринта, юніта чи фічі.
- Test strategy — документ, який описує процес тестування на рівні проєкту в цілому. Оскільки на проєкті можуть працювати сотні людей і безліч команд, інформація в test strategy є більш абстрактною (наприклад, типи тестування, підходи, наявність автоматизації). У test strategy зазвичай немає детального графіка (schedule).
Також існує Test policy — документ, що описує процес тестування на рівні організації або великої аутсорс-компанії (наприклад, SoftServe, EPAM, GlobalLogic).

За іншою, неофіційною версією, test strategy є частиною (розділом) test plan. У цьому контексті це просто абзац про те, які підходи планується використовувати для конкретної задачі. 

**Що таке traceability matrix?**
Traceability matrix (матриця відстежуваності, або трасування) — це таблиця, в якій співставляються два тестових документи.
Найпопулярніший вид — Requirements Traceability Matrix (test cases до вимог). У таблиці позначається (наприклад, хрестиком на перетині), який тест покриває яку вимогу. Це робиться, щоб переконатися у відсутності useless-тестів (які нічого не перевіряють) та непокритих вимог. Кожна вимога повинна мати мінімум два тести: один позитивний і один негативний.
Інші види:
- Test cases до багів (щоб відслідковувати, які тести знайшли які баги).
- Test cases до test cases (матриця залежностей). Використовується для виявлення залежностей між тестами. Залежність тестів — це погана практика. Наприклад, якщо є тест «Додати товар в обране» і тест «Видалити товар з обраного», другий тест повинен самостійно проходити кроки додавання товару, а не покладатися на виконання першого тесту. Кожен тест має бути незалежним.
- Impact analysis (аналіз впливу). Співставлення фічей до фічей (наприклад, якщо логін залежить від реєстрації). Це дозволяє зрозуміти, які саме ділянки системи необхідно перетестувати на регресії при внесенні змін розробником.

**Що таке баг, і чим дефект відрізняється від bug report?**
Баг (bug) — це недолік в програмі або невідповідність вимогам (те, що потрібно виправити).
Bug report — це документ (завдання для розробників), який описує цей баг для його виправлення.
Різниця між багом (bug) та дефектом (defect) відсутня. Це неформальна та формальна назви одного поняття. Згідно з силлабусом ISTQB, різниці між дефектом та багом немає.

**З чого складається bug report?**
- ID (унікальний ідентифікатор).
- Title (короткий опис, що відповідає на питання "Що? Де? Коли?").
- Steps to reproduce (кроки відтворення).
- Pre-conditions та post-conditions (опціонально).
- Actual result (актуальний результат — те, що система показує насправді).
- Expected result (очікуваний результат — те, що очікується за вимогами).
- Severity (ступінь впливу).
- Priority (пріоритет).
- Type (тип багу — опціонально).
- Assignee (розробник, на якого призначено баг).
- Status (статус багрепорту).
- Environment (середовище: версія програми, ОС, браузер, БД).
- Attachments (скріншоти, відео, логи) — обов'язкова частина.

**Що таке severity та priority? Наведіть приклади.**
Priority (пріоритет) — визначає, як швидко треба виправити баг (вплив на гроші та репутацію компанії). Зазвичай виставляється Product Owner-ом.
Severity (ступінь впливу) — показує, наскільки баг ламає програму та блокує функціонал. Виставляється тестувальником.

Приклади:
1. Високий priority та високе severity:
В інтернет-магазині не працює реєстрація, оскільки форма приймає лише номери телефонів іншої країни. Змінити локалізацію без реєстрації неможливо. Користувач не може зареєструватися і замовити товар. Це блокує основний функціонал (високе severity) та напряму впливає на прибуток (високий priority).
2. Високий priority та низьке severity:
Помилка в назві або логотипі компанії (наприклад, "Gogle" замість "Google"). Функціонал працює коректно (низьке severity), але це критично б'є по репутації компанії, тому вимагає негайного виправлення (високий priority).
3. Високе severity та низький priority:
На сайті магазину зламано пряме посилання на перехід у соціальну мережу (наприклад, YouTube). Частина функціоналу не працює (високе severity). Проте існує workaround — користувач може зайти на YouTube і знайти сторінку магазину самостійно. Тому пріоритет виправлення низький. На практиці баги з високим severity і низьким priority зустрічаються рідко.

**Опишіть життєвий цикл bug report.**
1. **New** — баг щойно створено.
2. **Open** — баг відкрито і взято до уваги.
3. **Assigned** — баг призначено на розробника.
4. **In Progress** — розробник працює над виправленням.
Далі можливі негативні сценарії:
- **Not a bug** — розробник відхиляє баг, аргументуючи тим, що система працює згідно з вимогами.
- **Duplicate** — баг дублює вже існуючий репорт. У такому випадку QA має перевірити оригінальний баг і слідкувати за ним.
- **Deferred** (відкладений) — баг не є критичним і переноситься на наступні спринти через брак часу.
Позитивний сценарій:
- **Fixed** (або **Ready for QA**) — розробник заявляє, що виправив баг.
5. **Verified** — QA зобов'язаний перевірити виправлення. Перевіряти потрібно завжди і за всіма розробниками (існує людський фактор: розробник міг забути закомітити, задеплоїти код на середовище, або виправити не ту частину коду).
Після перевірки:
- Якщо баг виправлено: статус змінюється на **Closed** (із зазначенням середовища перевірки).
- Якщо баг не виправлено: статус змінюється на **Reopened**, і баг повертається розробнику (цикл починається знову зі статусів Assigned/In Progress).

**Що робити, якщо розробник каже «це не баг» і відмовляється його виправляти?**
1. Надати розробнику вимоги, в яких чітко задокументовано, як саме має працювати функціонал.
2. Якщо вимоги суперечать одна одній або відсутні, необхідно звернутися до Product Owner або Business Analyst, щоб уточнити правильну логіку.

**Що робити, якщо розробник каже, що баг не відтворюється (cannot reproduce)?**
1. Зв'язатися з розробником (через дзвінок з демонстрацією екрану) і покроково показати процес відтворення багу.
2. Попросити розробника продемонструвати свій екран, щоб побачити, що він робить не так.
3. Локалізувати проблему: перевірити, чи збігаються Environment, версія програми, операційна система та браузер у QA та розробника.
4. Завжди прикріплювати до bug report відео, скріншоти та логи.

**Звідки брати інформацію про вимоги, якщо немає офіційного документа?**
Звертатися одразу до колег — це погана практика, оскільки час команди є цінним ресурсом. Правильний алгоритм дій:
1. Здійснити пошук за ключовими словами у внутрішній базі знань (наприклад, Confluence).
2. Переглянути описи завдань у Jira. User Stories (формату "As a user, I want to...") — це таски, в описі яких зазвичай міститься детальна інформація про функціональні очікування. Це і є неформальні вимоги.
3. Перевірити попередні test cases для цього функціоналу.
4. Якщо інформацію ніде не знайдено, тоді можна звертатися до колег.
5. Якщо колега не знає — звертатися до Tech Lead.
6. Якщо Tech Lead не знає — звертатися до Product Owner.
