Сьогодні ми розглянемо більше сотні різних типів тестування. Тестування програмного забезпечення — це класифікація різних дій тестування за категоріями. Кожна з цих категорій має визначену мету тестування, стратегію та результати. Метою типу тестування є перевірка програми, що тестується, для визначеної цілі.

Нижче представлено список типів тестування, які вдалося зібрати. За основу взята стаття Томаса Гамільтона «100 типів тестування» та інформація з глосарію ISTQB. Для зручності всі типи розділені за категоріями. Крім типів, також будуть згадані рівні та техніки тестування, оскільки в деяких ресурсах вони також називаються типами. Усі типи тестування, де не вказано, хто їх проводить, проводяться командою тестування.

**Категорія функціонального тестування:**

Функціональне тестування — це тип тестування, що базується на специфікаціях та вимогах до програми. Тобто ми тестуємо функціонал відповідно до вимог.

Requirements testing — це тип тестування, який підтверджує, що вимоги є правильними, повними, однозначними та логічно послідовними. Він дозволяє розробити необхідний і достатній набір тест-кейсів на основі цих вимог.

API тестування. API (Application Programming Interface, інтерфейс прикладного програмування) — це набір процедур, протоколів та інструментів для створення програмних додатків. Цей інтерфейс визначає, як одна програма повинна взаємодіяти з іншою, і дозволяє їм спілкуватися між собою. Тестування саме цих функцій називається тестуванням API. Воно визначає, чи розроблені API відповідають очікуванням щодо функціональності, надійності, продуктивності та безпеки. Ця техніка подібна до Unit-тестування тим, що націлена на рівень коду, але відрізняється тим, що зазвичай це завдання тестувальника, а не розробника.

Compliance testing перевіряє, чи розроблена система відповідає стандартам, процедурам та настановам. Зазвичай це виконується сторонніми компаніями, які пропонують сертифікацію [??? ПЕРЕВІРИТИ: сертифайт outgc Complete].

Conformance testing — це процес перевірки того, що реалізація відповідає специфікації, на якій вона заснована.

**Група типів, пов'язаних зі змінами (Changes related types):**

Sanity testing (яке часто хибно перекладають як «санітарне тестування») — це техніка тестування, яка визначає, чи нова версія програмного забезпечення працює достатньо добре, щоб прийняти її для серйозного тестування. За версією ISTQB — це те саме, що Smoke-тестування.

Confirmation testing або Retesting — це тип тестування, в якому інженер перевіряє виправлення дефекту, запускаючи тест, що виявив цей дефект.

Regression testing — це тип тестування, метою якого є виявлення дефектів програмного забезпечення після внесення змін до програми (наприклад, виправлення помилок або створення нових функцій). Це перевіряється шляхом повторного тестування. Тобто тестуються вже протестовані, готові модулі програми для того, щоб переконатися, що нові зміни їх не зіпсували.

Smoke-тестування — це техніка тестування, яка перевіряє основні компоненти програмної системи, щоб переконатися, що вони працюють належним чином. Воно проводиться відразу після створення збірки програмного забезпечення. Ключове слово в цьому визначенні — основні компоненти. Тобто ті, без яких далі немає сенсу тестувати (наприклад, логін, реєстрація та найголовніші функції програми).

Backward compatibility — це тип тестування, який перевіряє поведінку розробленого ПЗ зі старими версіями тестового середовища. Перекладається як сумісність з попередніми версіями, тобто що поточні тести можна прогнати на попередніх версіях і все працюватиме.

Age testing — це тип тестування, який оцінює здатність системи працювати в майбутньому, тобто в наступних версіях. Процес оцінювання проводиться командами тестування.

Comparison testing — це техніка тестування, яка порівнює сильні та слабкі сторони продукту з попередніми версіями чи іншими подібними продуктами. Може виконуватися тестувальниками, розробниками, менеджерами або продакт-оунерами.

Qualification testing — це тестування на відповідність вимогам та специфікаціям попереднього релізу. Зазвичай воно проводиться розробниками для клієнта, щоб продемонструвати, що програмне забезпечення відповідає визначеним вимогам.

**Група нефункціональних типів тестування:**

Нефункціональне тестування — це тип тестування, який зосереджений на перевірці програмного додатка на його нефункціональні вимоги (якість, швидкість, безпека тощо).

Security testing — це процес визначення того, що інформаційна система захищає дані та підтримує функціональність належним чином. Його можуть виконувати команди тестувальників або спеціалізовані компанії з тестування безпеки.

User Interface testing (UI тестування) — це тип тестування, який виконується для перевірки user-friendly інтерфейсу, тобто зручності використання програми.

Graphical User Interface Software testing (GUI тестування) — дуже схожий на UI тестування процес перевірки продукту, що використовує графічний інтерфейс користувача, щоб переконатись, що він відповідає специфікаціям та вимогам.

Load testing — це техніка тестування, яка завантажує систему чи пристрій та вимірює їх реакцію. Зазвичай його проводять performance-інженери.

Performance тестування — проводиться для оцінки відповідності системи або компонента визначеним вимогам по продуктивності. Його проводить performance-інженер. Цей термін також відомий як категорія, що об'єднує всі типи тестування навантаження (Load, Stress тощо).

Stress тестування — це техніка, яка оцінює систему або компонент на рівні або поза межами встановлених вимог. Простими словами, систему навантажують до її максимуму, до тієї точки, в якій вона ламається, і записується значення навантаження. Зазвичай його проводить performance-інженер.

Stability testing — це техніка, що намагається визначити, чи відбудеться збій програми, та перевіряє стабільність програмного забезпечення. Зазвичай його проводить performance-інженер.

Benchmark testing — це техніка тестування, яка використовує набори програм та даних, призначених для оцінки продуктивності апаратного та програмного забезпечення в певній конфігурації.

Зазвичай його проводить performance-інженер.

**Не-performance типи тестування:**

Localization testing — це тип тестування, зосереджений на адаптації глобалізованої програми до певної культури чи мови. Процес адаптації включає переклад користувацького інтерфейсу та документації, контроль формату дати та часу, увагу до грошових одиниць, правових особливостей, розкладки клавіатури, контроль символіки та кольорів, тлумачення символів та знаків.

Globalization testing — це метод тестування, що перевіряє належну функціональність продукту з будь-якими налаштуваннями культури чи мови, з використанням всіх можливих вхідних даних. Тут головне — перевірка відбувається для всіх країн.

Internationalization testing — це процес, що гарантує, що функціональність продукту не порушується, а всі повідомлення належним чином показуються під час використання різними мовами та в різних регіонах.

Configuration testing — це техніка тестування, що визначає мінімальну та оптимальну конфігурацію апаратного та програмного забезпечення, а також вплив додавання або модифікації ресурсів (пам'ять, диски, центральний процесор). Зазвичай це виконують performance-інженери. За глосарієм ISTQB немає такого поняття, як configuration testing, тому раджу дивитися на інших порталах.

Compatibility testing — це техніка тестування, що перевіряє, наскільки добре працює програмне забезпечення в певному апаратному чи програмному забезпеченні, операційній системі чи мережевому середовищі. Комп'ютерні системи вважаються сумісними, якщо вони можуть працювати в одному середовищі (наприклад, на одному апаратному забезпеченні), не впливаючи на поведінку одна одної. Сумісність слід перевіряти, коли нове або оновлене програмне забезпечення буде розгорнуто в середовищах, що вже містять встановлені програми.

Portability testing — це процес тестування для визначення переносимості програмного продукту.

Binary portability testing — це техніка, що перевіряє виконувану програму та її переносимість між системними платформами та середовищами (як правило, на відповідність специфікації Application Binary Interface).

Recovery testing — це техніка тестування, що оцінює, наскільки добре система відновлюється після збоїв, апаратних проблем чи інших катастрофічних ситуацій (наприклад, після Stress-тестування).

Upgrade testing — це техніка тестування, що перевіряє, чи можна належним чином використовувати ресурси, створені за допомогою старіших версій, і чи це не ускладнює навчання користувача.

Vulnerability testing — це тип тестування, що стосується безпеки програми та має на меті запобігти проблемам, які можуть вплинути на цілісність і стабільність програми. Його можуть виконувати внутрішні команди тестування або спеціалізовані компанії.

Це зазвичай виконується кінцевими користувачами як перевірка на зручність використання програми.

Conversion testing має дві різні версії. За однією версією — це тестування програм або процедур, що використовуються для перетворення даних з існуючих систем для використання в системах заміни. За другою версією — тестування перетворення виконується для перевірки зміни одного формату даних в інший (наприклад, у JPG), щоб ці дані могли використовуватися програмою.

Dependency testing — це тип тестування, що вивчає вимоги додатка щодо попереднього програмного забезпечення, початкових станів і конфігурації, щоб підтримувати належний функціональний аналіз.

Gorilla testing — це техніка тестування, зосереджена на інтенсивному тестуванні одного конкретного модуля. Gorilla testing неодноразово застосовує вхідні дані до одного модуля, щоб переконатися, що він працює належним чином і не має помилок. Виконується QA-командами зазвичай під час повного тестування.

Storage testing — це тип тестування, що перевіряє, чи програма зберігає файли даних у правильних каталогах і резервує достатньо місця для запобігання неочікуваному завершенню внаслідок браку місця.

**Техніки тест-дизайну:**

Equivalence partitioning (еквівалентне розділення) — це техніка, що розділяє вхідні дані на еквівалентні групи тестових даних, які поводяться однаково.

Boundary value analysis [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування, в якій тести перевіряють дані на проміжках та границях.

Exploratory testing — це техніка чорного ящика, що виконується без планування та документації. Вона вимагає більше навичок та досвіду, ніж Ad hoc тестування.

Session-based testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це тестування за допомогою сесій, використовується за допомогою тест-чартерів із визначеним часом, є підходом до дослідницького тестування.

Persona-based testing — це тестування на основі персон. Воно нагадує Use Case діаграми; їх використання визначає типи юзерів та описує поведінку певних категорій користувачів системи.

Error guessing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування, в якій інженер намагається вгадати потенційні помилки, щоб скоріше знайти дефекти.

Fuzz testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування програмного забезпечення, яка надає недійсні, неочікувані та рандомні вхідні дані.

Fault injection, розумними словами, — це елемент комплексної стратегії тестування, що допомагає тестувальнику зосередитись на тому, як тестована програма здатна обробляти винятки. Якщо перекладати дослівно, то Fault injection — це «ін'єкція помилки», коли спеціально вставляється в код або програму помилка, щоб перевірити, чи вона дійсно показується і чи програма здатна обробляти ці помилки.

Penetration testing — це підтип Security тестування, який оцінює безпеку комп'ютерної системи або мережі шляхом імітації атаки зі зловмисного джерела. Зазвичай проводиться спеціалізованими компаніями з тестування на penetration.

All-pairs testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка, яка представляє собою комбінаторний метод тестування і перевіряє всі можливі дискретні комбінації вхідних параметрів.

Pair testing — це техніка, за якої два члени команди працюють разом за однією клавіатурою, щоб перевірити ПЗ. Один проводить тестування, а інший аналізує або переглядає результат. Це можна робити між тестувальником і розробником (або бізнес-аналітиком) чи між двома тестувальниками, коли учасники по черзі керують клавіатурою.

State transition testing — це тестування на основі діаграми переходів та станів, що використовується в системах зі скінченним числом станів. Перевіряє всі можливі дії в різних станах системи і дозволяє проаналізувати, які переходи можна здійснювати.

Parallel testing [??? ПЕРЕВІРИТИ: назва типу тестування] також має два різні варіанти визначення. Перший: це тип тестування ПЗ, в якому кілька версій або підкомпонентів тестуються з однаковими вхідними даними на різних системах одночасно, щоб скоротити час виконання тесту. Мета — з'ясувати, чи поводяться стара та нова версії однаково, і переконатися, чи ефективніша нова. Друге визначення: це одночасне тестування кількох програм або компонентів, щоб скоротити час тестування.

White box testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування білого ящика, яка враховує внутрішню структуру системи та гарантує, що кожен оператор програми виконує призначену функцію. Зазвичай її виконують розробники програмного забезпечення. Робота ведеться безпосередньо з кодом.

Path testing — це типове тестування білого ящика, що має на меті задовольнити критерії покриття для кожного логічного шляху через програму. Зазвичай також виконує команда розробників.

Basis path testing — теж метод тестування білої скриньки, в якому тестові випадки визначаються на основі потоків чи логічних шляхів програми. Метою Basis path є визначення кількості незалежних шляхів, щоб можна було явно розрахувати необхідну кількість тестів для 100% покриття. Це передбачає виконання всіх можливих блоків програми з найменшою кількістю тест-кейсів для максимальної користі. Це гібридний метод тестування гілок та шляхів.

Workflow testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка End-to-end тестування за сценарієм, яка дублює певні робочі процеси, що очікувано виконуватиме кінцевий користувач.

Statement coverage — також тестування білого ящика, яке задовольняє критерій, за яким кожен оператор у програмі виконується принаймні раз під час тестування. Зазвичай виконується командою розробників.

Decision або Branch testing — це техніка тестування, за якої всі гілки вихідного коду програми тестуються принаймні один раз.

Condition testing [??? ПЕРЕВІРИТИ: назва типу тестування] — тип тестування, в якому кожна умова рішення перевіряється шляхом встановлення значення True або False. Зазвичай виконується групами автоматизованого тестування чи розробниками.

Multiple condition coverage [??? ПЕРЕВІРИТИ: назва типу тестування] — це тип тестування, в якому кожна умова виконується, коли вона істинна та хибна, принаймні один раз. Зазвичай створюється командами автоматизованого тестування.

Loop testing [??? ПЕРЕВІРИТИ: блок тестінг] — це техніка тестування білого ящика, яка використовує програмні цикли. Виконується командами розробників.

Mutation testing — це метод тестування, який передбачає зміну вихідного коду програми або байт-коду невеликими частинами, щоб перевірити ділянки коду, до яких рідко звертаються під час звичайного виконання тестів.

Scenario testing — це тестування, що використовує сценарії, засновані на гіпотетичній історії, щоб допомогти придумати складну проблему для середовища тестування.

**Підходи тестування:**

Black box (чорний ящик) — це метод тестування програмного забезпечення, що перевіряє функціональність програми без знань про код чи внутрішню структуру. Тобто маючи доступ тільки до User Interface та вимог, тести базуються на функціональності.

Gray box (сірий ящик) — це поєднання методології тестування чорного та білого ящиків. Це тестування на відповідність вимогам, але з використанням певних знань про внутрішню роботу (наприклад, про API або бази даних). Його можуть виконувати команди розробників або тестувальників.

White box (білий або скляний ящик) — це техніка, що базується на знанні внутрішньої логіки коду програми та включає такі тести, як покриття операторів, гілок, шляхів і умов (Statement testing, Branch testing, Path testing). Його виконують розробники програмного забезпечення, і тестувальники дуже рідко мають з ним справу.

Automated testing — це техніка тестування, що використовує інструменти автоматизації для контролю налаштування середовища, виконання тесту та звітування про результати. Виконується комп'ютером і використовується всередині команди тестування.

Scripted testing — це метод тестування, за якого тест-кейси розробляються та переглядаються командою перед виконанням. Manual scripts (мануальні сценарії) — це документи, які використовуються тестувальниками для виконання сценаріїв в рамках циклу тестування. Простими словами, це тестова документація. Як правило, Manual scripts включають загальну інформацію про тест, опис кроків, дані, очікуваний та фактичний результати, а також статус проходження.

Manual testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування, що передбачає перевірку всіх функцій, які виконують люди під час підготовки та використання даних в автоматизованій системі.

Negative testing (тест на невдачу) — це метод тестування, в якому вводять завідомо неправильні дані, щоб перевірити обробку помилок у програмі.

Positive testing — це метод тестування, в якому вводять валідні дані, щоб перевірити успішний сценарій.

End-to-end тестування — подібне до системного тестування і включає тестування повного програмного середовища в ситуації, яка імітує реальне використання. Тобто імітуються дії реального користувача від самого початку (відкриття веб-сайту) до цільової дії (додавання товару, оформлення замовлення та доставки).

Static testing — це форма тестування ПЗ, де програмне забезпечення фактично не запускається. Перевіряється головним чином правильність коду, алгоритму чи документа. Його використовує розробник, який написав код, або група для перевірки технічної документації.

Dynamic testing — на противагу статичному, це термін, що використовується для опису тестування динамічної поведінки коду. Програма запускається і тестується в процесі роботи.

Active testing — це тип тестування, що полягає у введенні тестових даних і аналізі результатів виконання.

Passive testing — це техніка, що полягає в моніторингу результатів працюючої системи без введення спеціальних тестових даних.

Code-driven testing — це техніка тестування, що використовує бібліотеки тестування (наприклад, xUnit або JUnit), які дозволяють виконувати модульні тести, щоб визначити, чи різні розділи коду діють належним чином. Виконується командами розробників або automation-інженерів.

Keyword-driven testing (також відоме як Table-driven або Action word тестування) — це методологія автоматизованого тестування, яка використовує ключові слова в якості команд. Може використовуватися групами як мануального, так і автоматизованого тестування, оскільки ключові слова роблять автоматизацію зрозумілою навіть без знання коду.

Modular-driven testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це техніка тестування, яка вимагає створення невеликих незалежних сценаріїв, що представляють модулі та функції програми.

Context-driven testing — це техніка Agile-тестування, що підтримує безперервну та творчу оцінку можливостей тестування в світлі виявленої потенційної інформації та її цінності для організації. Зазвичай виконується групами Agile-тестування.

Domain testing — це техніка тестування білого ящика, що містить перевірку того, що програма приймає лише дійсні вхідні дані. Зазвичай це роблять команди розробників, [??? ПЕРЕВІРИТИ: Планета] іноді — команди автоматизації тестування.

Model-based testing [??? ПЕРЕВІРИТИ: назва типу тестування] — це проектування та виконання необхідних артефактів для тестування на основі моделей.

Comparison testing — це тип тестування, під час якого сильні та слабкі сторони розробленого програмного забезпечення порівнюються із вже існуючими продуктами на ринку.

Concurrency testing — це багатокористувацьке тестування, спрямоване на визначення ефектів одночасного доступу до того самого коду програми, модуля або записів бази даних. Зазвичай його проводять performance-інженери.

Error handling testing — це тип тестування, що визначає здатність системи належним чином обробляти помилкові транзакції (подібно до Fault injection).

**Рівні тестування:**

Unit testing — це метод перевірки та валідації ПЗ, за якого програміст перевіряє, чи окремі одиниці вихідного коду придатні для використання. Зазвичай його проводить команда розробників, тестуючи найменші частинки коду — юніти або модулі.

Component testing — це техніка тестування, дуже подібна до модульного, але з вищим рівнем інтеграції. Тестування виконується в контексті програми, а не просто як перевірка окремого методу. Може виконуватися командами як тестувальників, так і розробників.

Integration testing — це етап тестування, на якому окремі модулі програмного забезпечення об'єднуються та тестуються як група.

System testing — це процес тестування інтегрованої апаратної та програмної системи для перевірки того, що система відповідає заданим вимогам.

[??? ПЕРЕВІРИТИ: інтерсітінг] — техніка тестування, яка перевіряє взаємодію між програмами і чи працюють вони правильно разом.

System integration testing — це процес тестування, який перевіряє співіснування однієї програмної системи з іншими.

Top-down integration testing — це техніка тестування, що передбачає початок із верхньої частини системної ієрархії в інтерфейсі користувача та використання заглушок для тестування зверху вниз. Поки не буде реалізовано всю систему (коли нижніх модулів ще немає), замість них використовуються заглушки.

Bottom-up integration testing — навпаки від Top-down, під час цього інтеграційного тестування спочатку розробляються модулі найнижчого рівня. Інші модулі інтегруються та тестуються один за одним. Поки вони не реалізовані, використовуються стаби (ті самі заглушки з іншою назвою).

Big Bang integration testing — це техніка тестування, яка інтегрує окремі програмні модулі лише тоді, коли вже все готово.

Hybrid integration testing — це гібридна техніка тестування, яка поєднує методи інтеграції Top-down і Bottom-up. Вона використовується для тестування додатків на основі клієнт-серверної архітектури.

Thread-based testing [??? ПЕРЕВІРИТИ: тестування на основі потоків] — слід проводити на початкових етапах тестування інтеграції, щоб ключові функції можна було перевірити для конкретного завдання чи потоку.

Acceptance testing — це формальне тестування, що проводиться, щоб визначити, чи відповідає система Acceptance критеріям [??? ПЕРЕВІРИТИ: Accept транскрипції], і щоб клієнт міг вирішити, приймати чи ні систему. Зазвичай виконується замовником.

Operational testing — це техніка тестування, що проводиться для оцінки системи або компонента в її робочому середовищі.

Alpha testing — це тип тестування програмного продукту, що проводиться на стороні розробника. Зазвичай виконується командою розробки (і розробниками, і тестувальниками).

Beta testing — це остаточне тестування перед випуском для комерційних цілей. Зазвичай це роблять кінцеві користувачі.

Gamma testing — це тип тестування перед випуском продукту, спрямований на виправлення незначних дефектів, виявлених у Beta-тестуванні. Як правило, виконується з максимальним залученням кінцевих користувачів.
Alpha, Beta і Gamma тестування відносяться до підкатегорії Acceptance тестування.

**Типи тестування поза категоріями:**

Agile тестування — це практика тестування ПЗ, яка відповідає принципам гнучкого маніфесту (Agile), наголошуючи на тестуванні з точки зору клієнтів, які використовуватимуть систему.

Assertion testing — це тип тестування, що полягає в перевірці, чи умови підтверджують вимоги до продукту.

Accessibility testing — це тип тестування, що визначає можливість використання продукту людьми з обмеженими можливостями (наприклад, з вадами слуху, зору чи ментальними захворюваннями). Процес оцінювання проводиться особами з обмеженими можливостями. Також Accessibility — це не тільки про інклюзивність чи фізичні особливості, а ще й про зручність для користувачів у специфічних ситуаціях (наприклад, водій за кермом або людина з візком).

Ad hoc тестування [??? ПЕРЕВІРИТИ: назва типу тестування] — це тестування, яке проводиться без планування та документації. Тестувальник намагається зламати систему, випадково пробуючи її функціональність.

Breadth testing — це набір тестів, які використовують всі функціональні можливості продукту, але не перевіряють детальні функції. Може використовуватися в різних контекстах (Integration, Sanity, Functional, System [??? ПЕРЕВІРИТИ: System Of ation через russion тестуваннях]).

Interface testing — це тестування, проведене для оцінки того, що система або компоненти правильно передають дані та керування одне одному. Зазвичай виконується командами тестування та розробників.

Install та Uninstall testing — це робота, зосереджена на тому, що потрібно буде зробити клієнту, щоб успішно встановити та налаштувати нове програмне забезпечення. Може включати повні або часткові процеси встановлення, видалення, оновлення. Зазвичай виконується інженером тестування разом із менеджером конфігурації. Простими словами, тестувальник встановлює програми або їх частини та видаляє їх.

[??? ПЕРЕВІРИТИ: назва типу тестування, ймовірно A/B testing] — це підхід тестування, щоб визначити, яка з двох систем або компонентів працює краще.

Risk-based testing — це тестування на основі ризиків. Допомагає пріоритезувати тести в системі та зробити розподіл функціональності на основі вірогідності виникнення різних дефектів.

Tours-based testing — це тестування на основі турів, що використовує різні метафори та ситуативні сценарії, на які накладається робота в системі.

Critical path testing — це основний тип тестових випробувань, під час якого значущі елементи та функції програми перевіряються щодо правильності роботи при стандартному використанні.

Extended testing — це тестування, спрямоване на дослідження всієї заявленої у вимогах функціональності, навіть тієї, що низько проранжована за ступенем важливості.
