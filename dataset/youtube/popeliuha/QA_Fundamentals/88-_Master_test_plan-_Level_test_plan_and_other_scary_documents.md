# 88. Master test plan, Level test plan and other scary documents

Source: https://www.youtube.com/watch?v=HgchQzPwBhs

Якщо ви Junior або Junior Pro і зараз шукаєте для QA або для силабусу відповідь на питання щодо документації (Master Test Plan, Level Test Plan, Master Test Report, Level Test Report тощо), у цьому матеріалі ми розглянемо ці типи документів. Те, що зараз називається критерієм входу на Junior і Junior Pro, насправді є частиною рівня Test Manager Advanced Level в ISTQB. Іспит на Test Manager потрібно здавати тільки тоді, коли ви плануєте бути тест-менеджером, тобто після рівня Senior. 

У цьому матеріалі пояснено, що таке ці документи, навіщо вони потрібні та з чого складаються. Детально розібрано Master Test Plan із використанням інформації безпосередньо з силабуса ISTQB.

Для підготовки до Knowledge Evaluation часто використовується перелік із максимальною кількістю документів та невеликими поясненнями до кожного з них. 

Master Test Plan (генеральний тест-план) — це комплексний тест-план, який охоплює всі роботи з тестування на проєкті. Master Test Plan є загальним зведенням усіх тест-планів.

Level Test Plan — це тест-план, що розробляється для кожного окремого рівня тестування (Unit, Integration, System, Acceptance, Alpha, Beta). Тест-плани можна писати і на найменші одиниці тестування, навіть на окремий тест-кейс, але розбивати тести на рівні доцільніше. Для проєктів, які використовують гнучкі методології (Agile, Scrum), рівні можуть замінюватися на ітерації або спринти, тобто тест-план створюється для кожного спринта. Чим більше тест-планів, тим, скоріш за все, більша команда і компанія. У невеликих компаніях зазвичай створюють менше документації.

Level Test Design — це детальний опис створення тест-кейсів, очікуваний результат і Test Pass Criteria (критерії проходження тесту). Документ містить слово "Level", оскільки його можна розписати за різними рівнями тестування.

Level Test Case — це тест-кейс по рівнях. У цих кейсах, які описані в Level Test Design, визначаються тестові дані для їхнього використання під час запуску тест-кейсів.

Level Test Procedure (тестова процедура) — детально описує, як запустити кожен тест, включаючи налаштування, передумови і кроки, які необхідно виконати.

Level Test Log — це тест-лог по рівнях. Тест-лог — це хронологічні записи того, що відбувається під час тестування. Уявіть, якби ви записували в блокноті або текстовому документі кожен свій крок і всі введені дані — це щось схоже на тест-репорт, але який вручну зазвичай не пишуть. Загалом тест-логи використовуються в автоматизації. Коли пишеться automation код, паралельно з діями описується суть виконання, щоб інші розуміли мету тесту і бачили в результатах, які кроки виконались. По суті, тест-лог — це список кроків, виконаних під час тестування, разом з усіма записаними даними.

Anomaly Report (аномальний репорт) — репорт будь-якої помилки (баг-репорт, issue, configuration issue тощо). Це стосується не тільки багів; наприклад, падіння сервера або поганої конфігурації, яку можуть налаштувати лише відповідні спеціалісти. Будь-які проблеми, зафіксовані в трекінгових системах (наприклад, Jira), які потребують виправлення, є Anomaly Report. До них можна віднести навіть невідповідність вимогам.

Level Interim Test Status Report — документ, який підсумовує всі дії та активності, виконані тестувальником до поточного моменту. Опціонально туди додають рекомендації та оцінку виконаних дій для покращення процесів у майбутньому.

Level Test Report — це результат тестування. Він складається з назви тесту, статусу (пройшов чи впав), дати запуску та інформації про систему, на якій він запускався. Залежно від проєкту та інструменту (наприклад, TestRail), можна відкрити тест-репорт для кожного тест-кейсу і переглянути, на якому кроці він впав. Документ називається Level Test Report, тому що тест-кейси розбиваються по рівнях або типах і запускаються як Test Suites, що генерує декілька відповідних звітів.

Master Test Report — це генеральний тест-репорт, у якому зібрано більшість запущених тестів. На основі цього документа проводиться аналіз і збирається статистика: кількість багів, проблем з автоматизацією, блокерів, витраченого часу на тестування тощо, що допомагає покращувати процеси.

Робочі продукти (тестова документація) — це документи, створені в процесі тестування. Вони відрізняються залежно від проєкту і компанії, але в більшості організацій зустрічаються чотири типи документів: Test Policy, Test Strategy, Master Test Plan та Level Test Plan.

Test Policy описує цілі організації та цілі тестування. Документ використовується для ознайомлення нових співробітників із підходами компанії, а також демонструється потенційним клієнтам для підтвердження якості тестування.

Test Strategy описує загальні, незалежні від проєкту методи тестування в організації. Він деталізує процес тестування на проєкті. Test Strategy зазвичай прив'язана до проєкту або великої групи людей, які працюють над продуктом.

Master Test Plan і Level Test Plan створюються для конкретного проєкту або окремої фічі. 

Наявність, відсутність та структура цих документів залежать від контексту. На деяких проєктах вони можуть бути об'єднані в один документ, на інших — розділені. Великі організації мають усі ці типи документів, тоді як менші компанії створюють менше письмових робочих продуктів.

Master Test Plan охоплює всю роботу з тестування на конкретному проєкті. Він включає інформацію про конкретні рівні тестування, зв'язки між ними та відповідні фази розробки програмного забезпечення. У Master Test Plan визначається, як тестувальники реалізовують стратегію тестування для проєкту — Test Approach (тестовий підхід). Не слід плутати тестовий підхід (Test Approach) усередині Master Test Plan із глобальним документом Test Strategy. Test Approach описує конкретний підхід для даного тестування, тоді як великий документ Test Strategy відповідає на глобальні питання: що, як, коли і хто буде тестувати.

Master Test Plan має обов'язково відповідати Test Policy та Test Strategy. Якщо виникають відхилення, вони повинні бути пояснені. Наприклад, якщо Test Strategy передбачає повне регресійне тестування перед випуском, але на поточному проєкті регресії не буде, у тест-плані пояснюється причина цього відхилення та описуються дії для пом'якшення пов'язаних ризиків. 

У невеликих проєктах із одним рівнем тестування (наприклад, системним), Master Test Plan та Level Test Plan часто об'єднуються. Якщо пов'язана з тестуванням діяльність (наприклад, керування конфігурацією) недостатньо задокументована, вона також має бути описана в Master Test Plan (наприклад, як тестові об'єкти доставляються команді).

Вміст Master Test Plan відрізняється залежно від проєкту, але загальні теми включають:
- Items to be tested — що буде і що не буде тестуватися.
- Characteristics to be tested — характеристики, які підлягають тестуванню (швидкість, стабільність тощо).
- Графік і бюджет тестування (узгоджені з проєктним бюджетом).
- Цикли виконання тестів та їхній зв'язок із планом релізу (Software Testing Life Cycle: планування, дизайн, аналіз, контроль тощо).
- Відносини та комунікація між тестуванням і суміжними відділами/ролями.
- Визначення елементів, що знаходяться в scope (скоупі) та поза ним для кожного рівня.
- Конкретні Entry Criteria та Exit Criteria (критерії входу та виходу) для кожного рівня тестування.
- Ризики та способи їхнього вирішення.
- Загальне управління тестуванням і відповідальність за виконання кожного рівня.
- Входи та виходи (Entry/Exit Criteria) для кожного Level Test Plan.

Level Test Plan описує конкретні дії в межах кожного рівня або типу тестування. Він доповнює Master Test Plan деталями, розкладом завдань та етапами, які не обов'язково охоплені в головному документі. Для Agile-проєктів ці плани можуть замінюватися планами спринту або планами ітераційного тестування.
